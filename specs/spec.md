# Спецификация протокола PoSoc (v0.14)

## 1. Назначение, принципы, модель угроз

### 1.1 Назначение

Цель — децентрализованная сеть доверия (**PoSoc — Proof of Social**), позволяющая каждому участнику отличать реальных людей от ботов/виртуальных аккаунтов **в пределах наблюдаемого им компонента социального графа**. Гарантии — условные и вероятностные, в терминах стоимости атаки.

### 1.2 Принципы

1. **Отсутствие инфраструктуры.** Нет корневых узлов, валидаторов, реестра или отдельного механизма упорядочивания. Сеть состоит из участников и их связей.
2. **Одноранговость.** Полномочий нет; каждый валидирует состояние сам.
3. **Субъективное локальное доверие.** Участник доверяет иерархиям, достижимым из его L0 (§6).
4. **Стоимость вместо альтруизма.** Протокол не предполагает честности: подтверждение ботов требует повторяющихся затрат. Подкуп и обман — источники этих затрат (§1.3).
5. **Публичность внутри компонента.** Записи публичны в компоненте связности; валидность — чистая функция данных.
6. **Эфемерность.** Все факты — автопродлеваемые TTL-объекты с мгновенным revoke; «купленного» факта не существует.
7. **Взаимность согласия.** Вход двусторонен (обе подписи / quorum); revoke и выход — односторонни. Молчаливого согласия нет.
8. **Эмерджентность иерархии.** Edges и levels — выводимое состояние, не записи.
9. **Время подписи.** Состояние — функция множества подписанных записей и текущего времени; порядок доставки семантики не имеет.
10. **Единая семантика revoke.** Каждый consent object X отзывается действием `X_REVOKE` того же подписанта; свежая подпись всегда сильнее старой.

### 1.3 Модель угроз

**Противник может:**
- создавать неограниченное число identity-ключей (Sybil) и контролировать связи своих узлов;
- создавать группы и `MEMBER_OF`-заявления (permissionless);
- получать связи с людьми через встречу, обман или подкуп;
- похищать identity-ключи: контролирующий ключ может опубликовать отзыв этого ключа (§2.3) и уничтожить личность;
- компрометировать устройства и их device-ключи (кража, угон, вредоносный код): это локальная транспортная проблема — device-ключ не даёт записей в графе и не угрожает личности; его отзыв — новый epoch реестра устройств, вне протокола (§7.3.1, §8.5);
- указывать задним числом $t_{sign}$ собственных записей;
- задерживать или скрывать записи при ретрансляции;
- смещать собственные часы.

**Противник не может (криптографически):**
- подделать подпись;
- создать или продлить consent object без требуемых подписей;
- включить участника в L0 без его подписи;
- отозвать чужой consent object;
- отозвать чужой ключ без владения его секретом;
- аннулировать poison mark без подписи создавшей стороны или fresh `FRIEND` пары;
- привязать группу к иерархии без живых внешних связей и quorum заявлений `MEMBER_OF`.

**Гарантии (в пределах допущений):**
- *Inclusion cost:* включение бот-компонента в человеческую иерархию требует $\approx t$ взаимных живых связей; линейно по порогу, рекуррентно ($\le T_{life}$).
- *Isolation:* `MEMBER_OF`-заявления без внешних живых связей не создают edges (disjoint count, §5.4); транспортная изоляция дублирует структурную (§2.2).
- *Backdating containment:* подделку задним числом устраняет `KEY_LOSS` — смерть ключа гасит все его записи, включая поддельные; без `KEY_LOSS` подделка необратима (принятая цена) (§3.2, §2.3).
- *Hijack localization:* окна сжимаются в $1+N$ раз; чужие marks угонщик не стирает; исключение — quorum отзывов, мгновенно.
- *Device-key containment:* компрометация device-ключа не создаёт записей в графе (device-ключи не подписывают записи, §2.3) и не раскрывает seed (§8.4); воздействие ограничено транспортным уровнем.

**Негарантии:** многоличность (§10.2); сговор выше порогов (§10.5); приватность (§11); мгновенная глобальная согласованность (§2.5); гарантированная доставка (§10.9–10.10); уничтожение личности угонщиком — контролируемый ключ может отозвать сам себя (восстановление — ротация, §7.3.4).

## 2. Архитектура

### 2.1 Identity

1. Личность — **ключ человека (identity-ключ)**: пара ключей $(x, pk)$, Ed25519 (§8), детерминированно выведенная из seed — мнемонической фразы (словарь BIP-39) с опциональной passphrase (§8.4; параметры — §9). Секрет не публикуется. Модель stateless: на устройстве ничего не хранится; восстановление личности = ввод фразы (и passphrase) на новом устройстве.
2. Регистрации нет: ключ существует, если фигурирует в живой записи. Sybil-устойчивость — граф, не реестр.
3. Один человек может владеть несколькими identity-ключами (§10.2); перенос истории протоколом не гарантируется (§7.3.4).
4. Отозванный ключ не существует: `KEY_LOSS` (§2.3) делает все записи ключа недействительными начиная с $t_{sign}$ записи `KEY_LOSS`. Записи ключа с большей $t_{sign}$ также недействительны по умолчанию: несуществующий ключ не может давать согласие. Правило §2.1.2 не «оживляет» ключ через его собственную запись отзыва.
5. Устройство не имеет identity-ключа и не является участником протокола. Устройство владеет **ключом устройства (device-ключом)** — транспортным ключом вне протокола (§2.2.1, §8.5): device-ключ не фигурирует в записях и не подписывает их. Во всех записях протокола $pk$ — identity-ключ человека.

### 2.2 Сеть без реестра

**Объекты узла:** база данных состояния (живые записи и архивный буфер), очередь синхронизации.

1. **Транспорт = социальный граф (уровень людей).** Сетевой узел — устройство человека; записи узла подписаны identity-ключом его владельца (§2.1). Запись ретранслируется только соседям (Neighbor, §13) — узлам людей с активной `FRIEND`. Транспортные соединения устанавливаются между device-ключами по правилу маппинга: соединение $d_u \leftrightarrow d_v$ валидно тогда и только тогда, когда между людьми $U$ и $V$ этих устройств есть активная `FRIEND` — устройства наследуют рёбра графа своих людей. Следствие (правило доступности): identity-ключ, вошедший в граф людей, делает доступными для взаимодействия все устройства своего владельца. Компонент связности — изолированная вселенная данных: записи человеческого компонента физически не достигают бот-кластеров (двойная изоляция). Свежий ключ без связей не получает трафика; установление `FRIEND` включает слив состояния. Аутентификация соединений (предъявление сертификатов device-ключей, распространение реестров устройств) — транспортный уровень, вне протокола: спецификация «transport-identity» экосистемы BeSoc (§8.5).
2. **Обработка записи:** проверка (подписи, каноническая форма, применимость, §2.4.8) → применение к базе данных → постановка в очередь синхронизации → рассылка соседям.
3. **Anti-entropy.** Узел периодически сверяет множества записей с каждым соседом по диапазонам времени и хешам. При расхождении недостающие записи загружаются. Утаивание записей соседом обнаруживается сверкой через других соседей. Риск единственного моста описан в §10.9.
4. **Обязательная зона хранения:** записи собственных связей и групп. Глубина остального — политика узла; правила relay и пропускная способность — **вне спецификации** (implementation-defined).
5. **GC horizons (минимум для корректности собственного состояния):**
   - записи пары — до $t_{last} + 2T_{life}$. Здесь $t_{last}$ — позднейшая $t_{sign}$ пары (лемма §3.4.1);
   - consent objects — до конца эффекта;
   - `KEY_LOSS` — до истечения TTL самой долгоживущей записи ключа на момент $t_{sign}$ отзыва (§2.3);
   - L0_GENESIS / адреса групп — хранятся владельцем адреса и любым узлом по политике.

### 2.3 Записи

Канонический CBOR (§2.7); $t_{sign}$ входит в подписываемую полезную нагрузку. Два класса: **consent objects** (TTL, автопродление, revoke; два типа: `FRIEND`, `MEMBER_OF`) и **actions** (мгновенный эффект).

**Подписанты — только identity-ключи людей (§2.1).** Всякий $pk$ в payload и в `sigs` — identity-ключ. Device-ключи не фигурируют ни в одном типе записей и не являются подписантами; закрытый набор типов записей (таблица ниже) и форматы §2.8 не изменяются.

| Record | Signers | Класс | Эффект |
|---|---|---|---|
| `FRIEND` | обе стороны пары | object, $T_{life}$ | friend instance пары (§3) |
| `FRIEND_REVOKE(P→O)` | подписант $P$ (один из пары) | action | прекращает instance + poison mark против $O$ (§3.2) |
| `MEMBER_OF(X, G)` | подписант $P$: $P=X$ — само-членство, $P \ne X$ — подтверждение | object, $T_{life}$ | членство «X member of G»: L0 и заявления в сообщества (§4, §5.2) |
| `MEMBER_OF_REVOKE(X, G)` | подписант $P$: $P=X$ — выход, $P \ne X$ — подтверждающий | action | отзыв: выход $X$ или отзыв чужого подтверждения (§4.2) |
| `L0_GENESIS(P, descriptor)` | $P$ (инициатор) | action | адрес L0 (§4.5) |
| `KEY_LOSS` | $P$ (сам ключ) | action | смерть ключа: инвалидация всех записей ключа (§2.3) |

`MEMBER_OF(X, G)` — единый тип членства, читается «X member of G»: подписант $P$: $P=X$ — само-членство (для $ID_{GH}$ — заявление о членстве в сообществе); $P \ne X$ — подтверждение члена другим участником (quorum-правило мгновенного исключения для чужих подтверждений — §4.2). Различение сценариев — по типу ID группы: $ID_G$ — базовая группа L0 (§4); $ID_{GH}$ — сообщество иерархии: живые `MEMBER_OF(P, GH)` образуют $R_{decl}(GH)$ и голосуют в C1-quorum (§5.2).

**Номенклатура `X_REVOKE`:** X — тип отзываемого consent object; подписант revoke совпадает с подписантом объекта. Событий слияний, вето, якорей, версий составов не существует.

**`KEY_LOSS` — смерть ключа.** Это action; подписант — сам ключ (`[self]`, §2.8). Назначение — тип + подписант; экземпляр на ключ один: второй `KEY_LOSS` того же подписанта игнорируется по общим правилам LWW (§2.4.4).

Эффект от $t_{sign}$ записи: все consent-записи ключа — `FRIEND` (в обе стороны) и `MEMBER_OF`, включая живые instance (экземпляры связи), — недействительны; consent-записи ключа с большей $t_{sign}$ также недействительны по умолчанию (§2.1.4). Ключ прекращает существование.

Для `FRIEND` с участием отозванного ключа instance прекращается. Вторая сторона остаётся живой, её записи действуют, а связь с новым ключом владельца создаётся обычным образом (§3.1).

Штрафов нет: `KEY_LOSS` не создаёт poison marks и не влияет на окна/decay. Созданные ключом `FRIEND_REVOKE` и метки против ключа сохраняют эффект, поэтому отмывание недоступно (§3.2, св. 4). `break` — это `FRIEND_REVOKE` (§3.2), а не `KEY_LOSS`.

Roster L0 и C1-кворумы пересчитываются существующими механизмами — мгновенный каскад (§4.3, §5.6).

Живость записи `KEY_LOSS` — не меньше TTL самой долгоживущей записи ключа на момент $t_{sign}$ отзыва. После истечения всех записей ключа его существование ничем не поддерживается; GC-горизонт — §2.2.5.

### 2.4 Время, конфликты, revoke-семантика, детерминизм

1. **$t_{sign}$** — заявленное автором время, подписано. **$now()$** — локальные часы узла. Состояние вычисляется «на момент» $\tau$.
2. **Правило будущего.** $t_{sign} > now + \Delta$ ($\Delta = 7$ сут.) — запись отбрасывается и повторно оценивается при следующей доставке (часы могли догнать это время). $t_{sign} \in (now,\ now+\Delta]$ — запись хранится и ретранслируется, но не применяется к состоянию, пока часы не догонят её время.
3. **Прошлое не ограничено.** Поздняя публикация принимается; ретроспективные эффекты ограничены горизонтами объектов (§3.4.1).
4. **Разрешение конфликтов (LWW).** Для записей одного **назначения** (identity: тип + все ключевые поля, включая направление для парных записей) действует запись с максимальным $t_{sign}$. Замещение — только при **строго большем** $t_{sign}$; при равенстве — запись с **меньшим** $H(\mathrm{record})$, вторая игнорируется. Единое правило для объектов и действий.
5. **Revoke-семантика (общая).** `X_REVOKE` обрезает живость соответствующих объектов **вперёд** от своей $t_{sign}$. Уничтожаются объекты того же назначения с $t_{sign} \le t_{sign}(\mathrm{revoke})$.

   Объекты с большей $t_{sign}$ представляют более свежее согласие и выживают.

   `X_REVOKE` покрывает consent objects. Смерть ключа — отдельный механизм `KEY_LOSS` (§2.3). Специфика `FRIEND_REVOKE` — binding и poison — описана в §3.2.
6. **Reconstruction.** Норматив — полная реконструкция: записи сортируются по $(t_{sign},\ H(\mathrm{record}))$ и применяются последовательно. Результат не зависит от порядка получения записей узлом. Инкрементальные вычисления допустимы при совпадении результата.
7. **Живость consent object на $\tau$:** $t_{sign} \le \tau < t_{sign}+T_{life}$ ∧ не отозван (§2.4.5) ∧ ключ-подписант не отозван (§2.3).
8. **Определение состояния.** Состояние = чистая функция (**хранимого** множества записей, $\tau$). Временное различие между множествами, хранимыми узлами, — норма; сходимость описана в §2.5.

   Правила игнорирования детерминированы. Запись игнорируется в следующих случаях:
   - неверная подпись;
   - неканоническая форма;
   - $t_{sign} > now+\Delta$;
   - неприменимость: `FRIEND_REVOKE` без bound instance (§3.2) или revoke объекта, которого нет в БД;
   - запись отозванного ключа с $t_{sign} > t_{sign}(\mathrm{KEY\_LOSS})$ (§2.3).

   Капы §2.6.2 и rate-limit §2.6.3 относятся к **отбору и замещению на уровне состояния**, а не к валидации. «Лишние» записи хранятся, но не считаются.
9. **Re-publish.** При изменении membership-статуса ключа (вступление в живую группу) узел повторно публикует свои живые `MEMBER_OF` (relevance — политика хранения/ретрансляции, не валидности).

### 2.5 Синхронизация и сходимость

При появлении записи используется gossip, а по расписанию — anti-entropy. Согласованность достигается в пределе; в каждый отдельный момент узлы имеют субъективные виды состояния.

Потребитель доверия всегда читает текущее состояние. Цензура соседа подавляет доставку, но не искажает семантику: задержанная запись применяется со своей $t_{sign}$.

### 2.6 Antispam (структурный)

1. **Relevance:** хранятся и ретранслируются записи, влияющие на состояние (`MEMBER_OF(P, GH)` от ключей $P$ вне живых $R_{str}(GH)$ не хранятся; re-publish — §2.4.9).
2. **Капы живых объектов на identity-ключ (уровень состояния):** ≤ 128 живых `MEMBER_OF` на identity-ключ — суммарно: L0-членства и заявления в сообщества (сверх — считаются 128 с наибольшими $t_{sign}$, тай-брейк по $H$); `FRIEND` и `MEMBER_OF_REVOKE` капом не ограничены. Правило подсчёта подтверждений: в кворумы входят только `MEMBER_OF` от текущих членов соответствующего $R_{str}$ (для L0 — §4.3.4a); подтверждение от не-члена хранится, не считается.
3. **Rate-limit:** обновление объекта с $t_{sign}' < t_{sign} + 7$ сут. не замещает прежнее.

### 2.7 Канонизация

Канонический CBOR (ключи отсортированы); пары ключей лексикографически; самосвязи запрещены; $H$ — BLAKE3; округления порогов — $\lfloor x + 10^{-9} \rfloor$.

### 2.8 Record formats (норматив)

Record = `{type, t_sign, payload, sigs}`; sigs — массив `{pk, sig}`, **отсортированный по pk**. Signing payload = канонический CBOR `{type, t_sign, payload}` — каждый подписант подписывает одни и те же байты. Идентичность записи = $H(\mathrm{record})$ (полные канонические байты); дедупликация по содержимому. Все `pk` — identity-ключи людей (§2.1, §2.3); device-ключи в форматах записей не участвуют.

| type | payload | sigs |
|---|---|---|
| `FRIEND` | `{x: pk, p: pk}` ($x < p$) | `[x, p]` |
| `FRIEND_REVOKE` | `{x: pk, p: pk}` ($x < p$) | `[r]` ($r \in \{x, p\}$ — отзывающий) |
| `MEMBER_OF` / `MEMBER_OF_REVOKE` | `{group: ID, member: pk}` | `[signer]` |
| `L0_GENESIS` | `{descriptor: tstr ≤ 128, initiator: pk}` | `[initiator]` |
| `KEY_LOSS` | `{}` | `[self]` |

`MEMBER_OF` читается как «X member of G». Поле `member` задаёт члена $X$. Если подписантом является $X$, это само-членство; для сообщества оно является заявлением о членстве, а его revoke — выходом или отзывом заявления. Если подписант не равен $X$, это подтверждение другого участника; его revoke — отзыв подтверждения. Подписант не дублируется в `payload`: он определяется подписью в `sigs`, как стороны `FRIEND` определяются полями `x` и `p`, а подписанты — массивом `sigs`. Для парных записей (`FRIEND`, `FRIEND_REVOKE`) payload задаёт одну и ту же каноническую пару $\{x, p\}$ с ограничением $x < p$ — оно действует для обеих записей; подписанты определяются массивом `sigs`: у `FRIEND` — обе стороны пары (`[x, p]`), у `FRIEND_REVOKE` — единственный отзывающий $r \in \{x, p\}$ (`[r]`). Направление разрыва определяется подписантом (`sigs`), а не порядком полей: poison mark создаётся против второго ключа пары — не-подписанта (§3.2).

Идентификаторы групп вычисляются из содержимого, без реестра: $ID_G = H(\texttt{"L0"} \Vert \texttt{descriptor} \Vert pk_{initiator} \Vert t_{sign})$ — базовая группа L0; $ID_{GH} = H(\texttt{"GROUP"} \Vert \texttt{descriptor} \Vert pk_{founder})$ — сообщество иерархии; типы идентификаторов различаются доменным тегом хеша. founder — pk первой (по $t_{sign}$) `MEMBER_OF` с `group: ID_GH` (техническая роль без привилегий). Поле `group` содержит $ID_G$ для L0 (§4) и $ID_{GH}$ для сообществ (§5.2). Доменное разделение BLAKE3 — по тегам типов; tie-break $H(\mathrm{record})$ — от полных канонических байтов. В `KEY_LOSS` отзываемый ключ — единственный подписант (`self`); идентифицирующих полей в `payload` нет (§2.3).

## 3. Связи

### 3.1 Instances

1. Связь — отношение пары ключей; не более одного текущего instance.
2. `FRIEND` пары с $t_c = t_{sign}$ создаёт instance. Instance с большей $t_c$ замещает прежний, который переходит в архив. Метки пары усекаются (§3.2.4).
3. Активная связь на $\tau$: instance не прекращён и не распался.

### 3.2 `FRIEND_REVOKE` и poison mark

**Реконструкция пары $(P, O)$.** Здесь $P$ — подписант рассматриваемого revoke, а $O$ — контрагент. Обозначения соответствуют конвенции §13.

1. **Instances.** Сначала записи `FRIEND` упорядочиваются по $t_c$. При равенстве используется меньший $H$.
2. **Binding.** `FRIEND_REVOKE(P→O)` с $t_{sign}=s$ привязывается к последнему instance $\ell$ записи `FRIEND` этой пары, для которого $t_c \le s$. Если подходящего instance нет, запись игнорируется.
3. **Разрешение по направлениям.** Направления $P \to O$ и $O \to P$ **независимы и не конфликтуют**. Взаимный revoke законен: каждая сторона отзывает своё согласие. В одном направлении, привязанном к $\ell$, действует запись с **максимальным** $t_{sign}$. При равенстве выбирается меньший $H$; остальные записи игнорируются.
4. **Эффект действующего `FRIEND_REVOKE(P→O, s)` для instance $\ell$:**
   - $t_b = \mathrm{clamp}(s,\ t_c(\ell),\ t_c(\ell)+T_{life}) = \min(s,\ t_c(\ell)+T_{life})$ (binding даёт $s \ge t_c$);
    - $\ell$ **прекращается** в $t_b$ (при нескольких действующих revoke — в наименьшем $t_b$);
   - **poison mark против $O$:** активен на $[\,t_b,\ \min(t_c(\ell)+T_{life},\ t_{relink})\,)$, где $t_{relink}$ — $t_c$ следующего `FRIEND` пары (нет — $\infty$).
    - При $s > t_c(\ell) + T_{life}$: интервал пуст — прекращение без mark.
5. **Встречный отзыв упразднён (v0.13).** Механизм встречного отзыва удалён. Пока ключ жив, точечного средства против подделки задним числом нет. Средство — `KEY_LOSS` (§2.3): смерть ключа гасит все его записи, включая поддельные.

**Из этих правил следуют свойства:**

1. **Направленность:** mark создаётся против контрагента отзывающего («травится покинутый»). **Взаимные revoke → обе стороны помечены.**
2. **≤ 1 mark на пару-направление, ≤ 2 на пару.** Метки разных пар стекируются; $N_X \le \deg(X)$ — инвариант сохраняется.
3. **Truce.** Свежий `FRIEND` пары усекает метки **обоих направлений** пары; окна выживающих связей обеих сторон расширяются немедленно; метки третьих лиц не затрагиваются.
4. **Отмывание недоступно.** Аннулирование mark требует fresh `FRIEND` пары (подписи обеих сторон, включая отзывавшего). Угонщик не стирает метки друзей жертвы; подделку задним числом устраняет только `KEY_LOSS` — смерть ключа гасит все его записи, включая поддельные (§2.3).
5. **Цена грифинга.** Цикл `FRIEND↔FRIEND_REVOKE` требует подписи «жертвы» на каждый `FRIEND`; собственные метки пары не накапливаются (≤2).
6. **Каскад revoke** против одного ключа — публичный сигнал компрометации (§7.4).

### 3.3 Decay

$$W_\ell(\tau) = \frac{T_{life}}{1+N_P(\tau)+N_O(\tau)},\qquad d(\ell)=\min\{\tau \ge t_c:\ \tau - t_c \ge W_\ell(\tau)\}$$

1. $W$ кусочно-постоянна. Чтобы найти $d(\ell)$, просматриваются моменты начала и конца меток против $P$ и $O$. Распад наступает не позднее $t_c + T_{life}$.
2. Активность $\ell = [t_c,\ \min(d(\ell),\ t_b))$.
3. **Необратимость — относительно текущего множества записей.** Расширение окон отодвигает распад выжившего, но не оживляет распавшийся instance. Позднее прибытие записи может переписать историю пары; это осознанное следствие правила «прошлое не ограничено» (§2.4.3). Оживить пару можно только новым `FRIEND`.

### 3.4 Леммы и пример

1. **GC horizon.** Mark не создаёт эффектов позже $t_c(\ell) + 2T_{life}$: сам живёт $\le t_c + T_{life}$ и влияет на окна связей, созданных не позже чем на $T_{life}$ позже.
2. Все производные величины вычисляются из хранимого множества записей без истории применения.

*Пример* ($T_{life}=12$ мес., проверен):
- `FRIEND_REVOKE(P_1→O_1)` в $t{=}2$: подписант — $P_1$, instance $t_c{=}0$. Возникает mark $[2,12)$ против $O_1$.
- У связи $(O_1, X_2)$ с $t_c{=}0$ окно составляет 6 мес., распад — $t{=}6$.
- Truce — свежий `FRIEND` пары $(P_1, O_1)$ в $t{=}4$ — усекает mark. Окно $(O_1, X_2)$ немедленно становится равным 12 мес., распад — $t{=}12$. Выжившая связь спасена.
- У пары $(P_1, O_1)$ свежий instance действует до $t{=}16$.
- Взаимный `FRIEND_REVOKE(O_1→P_1)` в $t{=}3$ (подписант — $O_1$) добавил бы mark против $P_1$ на $[3, 12)$. Этот mark независим от mark против $O_1$.

## 4. Базовые группы (L0)

### 4.1 Принцип

L0 — реальные малые группы. Membership — **непрерывный двусторонний предикат**: само-членство ∧ подтверждения группы ∧ link-опора. Ни ростер, ни запись не включают $P$ без подписи $P$; пребывание — при поддержке большинства. Вход двусторонен; revoke и выход — односторонни.

### 4.2 Объекты

- **`MEMBER_OF(X, G)`** — «X member of G» (TTL, продлевается клиентом подписанта): подписант $P$: $P=X$ — само-членство; $P \ne X$ — подтверждение членства другого. Тип членства един для всех групп; различение сценариев — по типу ID группы: $ID_G$ — базовая группа L0, $ID_{GH}$ — сообщество иерархии, где живые `MEMBER_OF(P, GH)` образуют $R_{decl}(GH)$ и голосуют в C1-quorum (§5.2).
- **`MEMBER_OF_REVOKE(X, G)`** с подписантом $X$ — отзыв само-членства: membership $X$ прекращается немедленно, односторонне (выход).
- **`MEMBER_OF_REVOKE(X, G)`** с подписантом-подтверждающим — отзыв своего подтверждения; **quorum отзывов** роняет поддержку немедленно — это и есть исключение (события EXPEL не существует).

### 4.3 Roster computation (growth priority)

Membership — это **результат детерминированного алгоритма** на $\tau$:

1. **Candidates:** все ключи $X$ с живым само-членством `MEMBER_OF(X, G)` (подписант = $X$).
2. **Cap-30 (до раундов):** при $>30$ кандидатов берутся 30. Отбор идёт в следующем порядке: (i) по числу живых `MEMBER_OF(·, G)` от других кандидатов (подписант ≠ кандидат, счёт по уникальным подписантам; по убыванию); (ii) при равенстве — по более свежему $t_{sign}$ само-членства `MEMBER_OF`; (iii) при равенстве — по $pk$ (по возрастанию). Непопавшие в отбор ключи остаются кандидатами. Их записи не теряются, повторная публикация не нужна.
3. **Growth priority:** начальный roster содержит **всех** отобранных кандидатов. Присоединение никогда не блокируется маргинальностью incumbents. Если укрупнённые пороги делают incumbents недействительными, incumbents удаляются раундами (**squeeze-out** — принятая семантика, §10.16).
4. **Synchronous rounds:** на каждом раунде **одновременно** удаляются все, нарушающие относительно текущего roster:
   (a) **кворум подтверждений (member-of-quorum):** живых `MEMBER_OF(·, G)` от текущих членов (подписант ≠ кандидат; само-членство в кворум не входит) ≥ $\lfloor |M|/2 \rfloor + 1$;
   (b) **cohesion:** активных связей с текущими членами ≥ $\lfloor |M|/2 \rfloor + 1$.
    Раунды повторяются до стабилизации. Результат **sound**: инварианты выполнены. **Maximality не гарантируется** и не заявляется. Вычисление детерминировано.
5. **Freshness tie-break:** любые равные притязания в L0-вычислениях (cap, равные счёты) → fresher $t_{sign}$, затем $pk$.
6. **Quench:** $|M_{act}| < 4$ → roster пуст; edges от группы отваливаются мгновенным каскадом (§5.6).

### 4.4 Динамика: две скорости

- **Явные действия — мгновенны:** `MEMBER_OF_REVOKE` от себя (выход), quorum `MEMBER_OF_REVOKE` от подтверждающих (исключение), потеря cohesion (удаление раундом при следующем пересчёте).
- **Угасание — ≤ $T_{life}$:** expire без продления покрывает мёртвые узлы.
- **Вступление/возвращение:** материализация = живое само-членство `MEMBER_OF` + подтверждения других членов; после угасания поддержки — только заново набранный quorum. В норме продление тихое.
- Roster мгновенно входит в $R_{str}$ → пороги → edges (§5.6).

### 4.5 Genesis

`L0_GENESIS(initiator, descriptor, t_sign)` задаёт адрес $ID_G$ (§2.8) — без привилегий. Группа жива, когда ≥ 4 участников удовлетворяют §4.3 (их само-членства и взаимные подтверждения `MEMBER_OF` — обычные объекты). Церемоний нет: genesis — адрес, остальное — непрерывный предикат.

## 5. Эмерджентная иерархия

### 5.1 Принцип

Явные акты создают связи и членство (`MEMBER_OF`) в группах L0 и сообществах. Edges, levels и валидность — выводимое состояние, которое непрерывно пересчитывается.

### 5.2 Заявления о членстве (`MEMBER_OF`)

1. **`MEMBER_OF(P, GH)`** — запись членства для сообщества-вершины иерархии ($ID_{GH}$), такая же, как в L0. Подписанное $P$ утверждение означает: «P member of GH» («я состою в $GH$»). Живые записи `MEMBER_OF(P, GH)` образуют $R_{decl}(GH)$. Каждая такая запись является голосом в C1-quorum **каждого** ребра $G \to GH$, если $P \in R_{str}(G)$. TTL равен $T_{life}$ и тихо автопродлевается (rate-limit §2.6.3). Один `MEMBER_OF` голосует во всех соответствующих quorum: один человек — одно согласие. Disjoint count по уникальным pk исключает двойной счёт.
2. **`MEMBER_OF_REVOKE(P, GH)`** — мгновенный односторонний отзыв (лёгкое возражение): живость `MEMBER_OF` обрезается в $t_{sign}$; quorum падает → edge отрывается мгновенно. Осцилляция REVOKE↔`MEMBER_OF` самонаказуема (отрыв мгновенный, возврат — через $T_{hold}$).
3. **Адрес группы** $ID_{GH}$ (§2.8); имя — не identity (§10.1); identity сообщества — структура. Различение сценариев членства — по типу ID группы: $ID_G$ — базовая группа L0 (§4), $ID_{GH}$ — сообщество иерархии.
4. **Isolate** — группа без живых детей. Для неё $R_{str} = \varnothing$, а адрес не хранится сетью: его хранит владелец. Такая группа подключается только через bootstrap (§5.5). Записи `MEMBER_OF(P, GH)` от ключей $P$, не входящих в живой $R_{str}$, к $GH$ не хранятся (§2.6.1, §2.4.9).

### 5.3 Rosters

1. $R_{decl}(GH)$ содержит участников с живыми `MEMBER_OF(P, GH)`. Это заявления, **не носители доверия, в порогах не участвуют**.
2. $R_{str}(GH) = \bigcup_{G \in \mathrm{children}(GH)} R_{str}(G)$ по уникальным pk; для L0 — активный roster §4; isolate — $\varnothing$.
3. Участник «в иерархии» ⟺ состоит в валидной L0, транзитивно привязанной к доверенному компоненту.
4. Разделение ростеров исключает циркулярность: заявления о членстве не подменяют структурный roster.

### 5.4 Thresholds и disjoint count

1. **Disjoint count:**

$$U_{G_1 \Rightarrow G_2} = \big|\{\,X \in R_{str}(G_1):\ \exists\, O \in R_{str}(G_2) \setminus R_{str}(G_1),\ \text{связь } (X,O) \text{ активна}\,\}\big|$$

2. **Пороги** ($avg = (|G_1|+|G_2|)/2$, $\rho = |big|/|small|$, $f = f(avg)$, $\kappa = \kappa(avg)$):

$$f(m) = \begin{cases} 0.5, & m < 30 \\ 0.05 + 0.45 \cdot 1.5^{-\log_{10}(m/30)}, & 30 \le m \le 10^4 \\ 0.05 + 0.1618 \cdot 4^{-\log_{10}(m/10^4)}, & m > 10^4 \end{cases}$$

$$\gamma(\rho) = \min(1,\ f + c(\rho-1)),\ c = 0.25;\qquad \kappa(m) = \min(\lfloor m/2.5 \rfloor,\ 4500)$$

$$t_{big} = \min\big(|big|,\ \max(\lfloor f \cdot |big| \rfloor,\ \kappa) + 1\big),\qquad t_{small} = \min\big(|small|,\ \max(\lfloor f \cdot |small| \rfloor,\ \lfloor \gamma \cdot |small| \rfloor,\ \kappa) + 1\big)$$

3. **Пара проходит** ⟺ $U_{G_1 \Rightarrow G_2} \ge t_{G_1}$ ∧ $U_{G_2 \Rightarrow G_1} \ge t_{G_2}$.
4. **Инварианты:**

   (i) При непустых внешних частях и полной взаимной внешней связности пара проходит. При большом пересечении ростеров внешние части малы, поэтому оговорка существенна.

   (ii) $t \le |side|$.

   (iii) Равные пары: $t = \min(m, \max(\lfloor f\,m \rfloor, \kappa(m)) + 1)$.

   (iv) $\rho{=}1$, $m<30$: $t = \lfloor m/2 \rfloor + 1$.

   (v) Асимметрия — цена до единогласия малой стороны.
5. **Лемма (инъекция одного ключа).** Угнанный аккаунт + 30 сибил-ключей: $U_{G_1 \Rightarrow G_2} = 30 \ge t_{G_1}$, но $U_{G_2 \Rightarrow G_1} = 1 < t_{G_2}$ — двусторонность отбивает инъекцию через один человеческий ключ.

### 5.5 Live edge: условия, активация, bootstrap, freeze

**Статусы групп:** *isolate* означает 0 живых детей, $R_{str} = \varnothing$ и отсутствие уровня. *vertex* означает 2 живых ребёнка; это предел бинарности (см. «Бинарность объединений» ниже). *free group* означает 1 живого ребёнка. Такой статус возникает только понижением vertex: edge грандфатерится, а приём одного ребёнка и привязка вверх выполняются на общих основаниях.

**Edge $G \to GH$ жив на $\tau$ ⟺ непрерывно:**

- **C1 (consent):** ≥ $\lfloor |G|/2 \rfloor + 1$ участников $R_{str}(G)$ имеют живые `MEMBER_OF(P, GH)`;
- **C2 (corroboration):** для **каждого** живого ребёнка $G_2 \in \mathrm{children}(GH) \setminus \{G\}$ — при бинарности объединений (см. ниже) он единственный — пара $(G, G_2)$ проходит;
- **C3 (acyclicity):** не существует пути $GH \Rightarrow^* G$ по живым рёбрам.

**Активация.**

- **Attach к живой группе:** у $GH$ есть ≥ 1 живого ребёнка и свободный детский слот, то есть живых детей меньше двух. Кроме того, $R_{str}(G) \ne \varnothing$, иначе C1 невыполним. Если C1–C3 выполняются непрерывно $T_{hold}$, ребро активируется. Проверка пар кандидата со всеми живыми детьми делает активацию безопасной для этих детей.
- **Freeze ∥ hold window.** Freeze не приостанавливает накопление окна. Активация происходит в $\max(\text{конец freeze},\ \text{конец окна})$.
- **Freeze:** после `L0_GENESIS` и bootstrap-активации вершины действует $T_f$. Freeze блокирует только **новые** активации рёбер вверх; существующие рёбра и дети не затрагиваются.

**Bootstrap пустой группы $GH$:**

1. **Candidates** $K$: группы с живым C1-quorum к $GH$.
2. **S-set:** $S \subseteq K$, $|S| = 2$ — правило бинарности (см. ниже); все пары **внутри $S$** проходят. Существование одного $S$ достаточно — кандидаты вне $S$ ничего не блокируют (anti-DoS: сибил без внешних связей не входит ни в одно $S$).
3. **Окно:** для фиксированного $S$ условия всех его членов должны выполняться непрерывно $\ge T_{hold}$. Изменение состава $S$ (потеря члена или падение пары) перезапускает окно **этого** $S$. События кандидатов вне $S$ это окно не перезапускают.
4. **Выбор при активации:** все $S$ имеют размер 2, поэтому среди $S$ с завершённым окном порядок определяется окном с более ранним стартом; при равенстве — лексикографически наименьший отсортированный список $ID$.
5. **Эффект:** $\mathrm{children}(GH) = S$; $R_{str}(GH) = \bigcup$; freeze $T_f$ для $GH$; прочие кандидаты присоединяются после по общим правилам attach.

Одновременные активации оцениваются в детерминированном порядке — по $(t_{sign},\ H)$ объекта-условия; активированное ребро цикла создать не может (C3).

**Бинарность объединений.** Сообщество объединяет не более двух групп, поэтому живых детей у $GH$ не больше двух. Attach возможен, только пока живых детей меньше двух. Bootstrap активирует ровно двух кандидатов. Дальнейший рост иерархии идёт через бинарные объединения: новая вершина создаётся над двумя сообществами. Структура, в которой оказалось более двух живых детей, пересчитывается на общих основаниях (§5.6.1, §5.6.2).

### 5.6 Динамика: мгновенный пересчёт

1. **Detach — мгновенный.** Провал C1 у edge **или** провал любой пары $(G_i, G_j)$ → **оба** edge пары отпадают немедленно; $GH$ пересчитывается немедленно.
2. **Понижение.** Если живых детей $< 2$, статус меняется. При 1 ребёнке vertex становится **free group**: edge грандфатерится, $L = 1 + L(\text{ребёнка})$. При 0 детей группа становится **isolate**, а восходящие edges отваливаются **тем же пересчётом**, поскольку C1 при пустом $R_{str}$ невыполним. Изолят привязывается **только bootstrap-ом**. Рёбра детей сохраняются; каскад — полный мгновенный пересчёт без искусственных задержек.
3. **Levels:** $L(GH) = 1 + \max_G L(G)$; isolate — без уровня; метаданные. При бинарности объединений (§5.5) ширина вершины равна 2: $D \approx \log_2(N_{pop}/\overline{|L0|})$.
4. **Параллелизм:** multi-parenting — штатное состояние DAG; дети не блокируются ничем, кроме собственного freeze и свободного детского слота родителя (не более двух детей, §5.5).
5. **Пересчёт:** выполняется непрерывно. Пороги всегда рассчитываются по текущим структурным численностям (дрейф — §10.11).

### 5.7 Возражения и выход

1. **Лёгкое** — `MEMBER_OF_REVOKE`: quorum C1 падает, edge отрывается мгновенно.
2. **Тяжёлое** — `FRIEND_REVOKE` (§3.2).
3. **Выход группы из родителя** — массовый `MEMBER_OF_REVOKE` членов $G$; отдельного события нет.

### 5.8 Изоляция ботов

`MEMBER_OF` permissionless, но: quorum L0 контролируются людьми; isolate имеет пустой $R_{str}$; disjoint count исключает co-membership; каждая пара на пути бот-поддерева в человеческую иерархию требует живых человеческих связей с TTL ≤ $T_{life}$. Одиночные edges (free groups) обхода не открывают: соединяющее ребро встречает сестёр (self-healing — оторванное от людей поддерево теряет корроборацию не позже $T_{life}$).

### 5.9 Мотивация связей

Алгоритм не регламентирует, кого подтверждать; предполагается, что реальных связей достаточно для связывания графа.

## 6. Потребление доверия

### 6.1 Proof membership

Доказательство — **поддерево**, а не путь. Для каждого parent на пути предъявляются все живые дети, их перекрёстные связи (C2), численности $R_{str}$ и живые `MEMBER_OF(P, GH)` (C1). Кроме того, предъявляется собственная L0 заявителя: само-членства, подтверждения `MEMBER_OF` и связи.

Причина такого формата — валидность одного edge является свойством всего множества детей. Сильный режим — верификация по собственной replica, то есть чистой функции состояния. Заявления о членстве в доверии не участвуют. Commit-structures (Merkle-корни поддеревьев) для лёгких верификаторов — roadmap (§11).

### 6.2 Субъективная оценка

Доверенное множество — транзитивное замыкание родителей L0 верификатора. К нему добавляется политика верификатора: размер, возраст и аномалии (§7.4). Глобального флага «человек» нет.

Практическая картина такова: люди образуют гигантский компонент, а бот-кластеры остаются изолированными компонентами — структурно и транспортно.

### 6.3 Spot-check (SHOULD; расшифровка)

**Проблема.** Prover может утаить неблагоприятные записи (`MEMBER_OF_REVOKE`, `FRIEND_REVOKE`, распад связей). Верификатор без полной копии не видит неполноту предъявленного множества — это главный вектор обмана лёгкого верификатора.

**Механизм.** Верификатор выбирает $k$ случайных участников из предъявленных rosters и запрашивает у них записи, затрагивающие proof. Эти записи позволяют проверить живость `MEMBER_OF` и активность связей поддерева.

Транспорт запроса — social graph верификатора / anti-entropy pull к собственной replica. Если полученные записи расходятся с предъявленными, результат — reject.

**Свойства.** Записи публичны в компоненте. Поэтому утаивание записей prover'ом не мешает другим узлам владеть этими записями. Вероятность обнаружения утаивания — $\approx 1-(1-p)^k$, где $p$ — доля опрошенных, владеющих противоречащей записью. Запросы liveness — вне гарантий.

**Пределы.** Проверка ограничена, если весь компонент согласованно скрывает записи или у верификатора нет независимых путей к данным. Сильный режим с собственной replica от этих пределов свободен.

**Статус:** SHOULD — политика клиента; на консенсус не влияет.

## 7. Защитные механизмы

### 7.1 Гистерезис и freeze

$T_{hold}$ — окно непрерывного выполнения условий **перед активацией**. Это время для уведомлений, возражений и дороста связей.

Отрыв происходит мгновенно. Асимметрия осознана: включение медленное, отторжение немедленное. Флаппинг подавляется за счёт затрат на повторное включение.

$T_f$ защищает от накачки и ротации топологии. Этот период идёт параллельно hold window.

### 7.2 Decay и poison

Защита сочетает окна $T_{life}/(1+N)$, накопление меток по разным парам, конечный срок меток и truce.

Взаимные marks (≤2 на пару) — осознанная цена симметрии revoke. Покинутый с обеих сторон получает двойное сжатие только от этой пары. Каскад против одного ключа по-прежнему ограничен $\deg$.

### 7.3 Hijack, потеря ключа, боты

1. **Градации инцидентов.** Модель ключей (§2.1) разделяет инциденты по классам:
   - **(а) Потеря, кража или компрометация устройства.** Инцидент локален и транспортен: отзывается device-ключ — исключением из реестра устройств с новым epoch, вне протокола (§8.5). Личность, её identity-ключ и граф не затронуты; `KEY_LOSS` не нужен. Компрометация устройства ≠ компрометация личности: seed не вводится на обычные устройства — только на устройство-инициатор восстановления (§8.4).
   - **(б) Компрометация или утрата seed / identity-ключа.** Прежняя семантика: `KEY_LOSS` (§2.3), при угоне — quorum-отзыв друзьями и ротация (п. 4 ниже).
2. **Hijack (угон identity-ключа).** Друзья публикуют `FRIEND_REVOKE` и `MEMBER_OF_REVOKE` (quorum). Окна сжимаются в $1+N$ ($T_{life}{=}12$ мес., $N{=}6$ — изоляция за ≈1.7 мес.). Обновления требуют подписей друзей, а созданные друзьями marks угонщик не аннулирует (§3.2.4).

   Угонщик может опубликовать `MEMBER_OF_REVOKE`: рёбра отвалятся мгновенно, но этот вред обратим. Указание задним числом `FRIEND_REVOKE` от имени жертвы точечными средствами не нейтрализуется. Свежая подпись — правило разрешения конфликтов (§3.2.3); отметку подделки эта подпись не стирает.

   Средство против подделки задним числом — `KEY_LOSS` (§2.3). Полный отзыв ключа гасит все его записи, включая поддельные. Поэтому `KEY_LOSS` рекомендуется при любом подозрении на компрометацию, даже разовой. Компрометация device-ключа сюда не относится — см. §7.3.1(а).
3. **Честное восстановление.** После личной переверберации друзья подписывают `FRIEND`. Marks обоих направлений аннулируются, instances чисты, затем заявления `MEMBER_OF` возобновляются. «Штрафа переживания» нет.
4. **Потеря ключа (ротация) — рецепт.** Если контроль над секретом сохранён при потере или компрометации, первым шагом служит `KEY_LOSS` (§2.3). Все записи ключа мгновенно становятся недействительными, без poison marks и штрафов. Затем новый identity-ключ вступает в L0: для этого нужны само-членство `MEMBER_OF` и кворум подтверждений. Новый identity-ключ выводится либо из того же seed — новым путём деривации (§8.4, §9), либо из новой мнемонической фразы; выбор — за владельцем, спека фиксирует оба варианта как валидные. После этого контрагенты переподписывают связи (`FRIEND` — truce чистит метки пар).

   Если контроля над секретом нет (угон), старый ключ выводится друзьями через quorum `MEMBER_OF_REVOKE`. Само-выход недоступен, поскольку ключ у вора; механизм hijack описан в §7.3.2.

   Marks привязаны к ключу и не переносятся. Вору quorum не собрать; ботам ротация бесполезна. Непрерывность «тот же человек» — негарантия (§10.2).
5. **Боты.** Не проходят порогов без человеческих связей (§5.8).

### 7.4 Обнаружение аномалий (advisory)

Для обнаружения аномалий рассматриваются следующие признаки:
- churn (циклы `FRIEND`/`FRIEND_REVOKE`, осцилляции);
- каскадные revoke против одного pk;
- массовые `FRIEND` после каскада («прощение-фишинг»);
- синхронные `MEMBER_OF`/`MEMBER_OF_REVOKE`, спам адресов, набеги, namespace-спуфинг;
- звёздные топологии;
- распределения степеней/плотности;
- синхронность операций;
- динамика L0 (синхронные вступления/отзывы, squeeze-out паттерны, growth-атаки);
- накачка уровней, цепочки одиночных детей;
- DAG-специфика (штормы привязок, близнецы-родители).

## 8. Криптография и объёмы

1. **Подписи:** Ed25519 (pk 32 Б, sig 64 Б); подписант записей — всегда identity-ключ (§2.1, §2.3); интерфейс допускает постквантовые схемы.
2. **Хеши:** BLAKE3, доменное разделение по типам записей (§2.8).
3. **Канал уведомлений (опционально):** $s_{uv} = \mathrm{HKDF}(\mathrm{X25519}(x_u, pk_v))$, где $x_u$, $pk_v$ — identity-ключи людей $u$ и $v$ (не device-ключи), — координация продлений и подписей `FRIEND`; не источник истины.
4. **Identity-ключ: деривация из seed.** Seed = мнемоническая фраза BIP-39 (словарь 2048 слов) + опциональная passphrase («25-е слово»). KDF: PBKDF2-HMAC-SHA512 по BIP-39 (salt = «mnemonic» ‖ passphrase) — 512-битный seed; identity-ключ $(x, pk)$ — hardened-деривация Ed25519 по SLIP-0010/BIP-32-совместимой схеме; конкретный путь — параметр §9. Требование детерминизма: одинаковые (мнемоника, passphrase, путь) дают одинаковый $(x, pk)$ на всех платформах. Seed вводится только на устройство-инициатор восстановления; на обычных устройствах seed не хранится и не вводится — изоляция: компрометация устройства ≠ компрометация личности (§7.3.1). Ротация без смены фразы — новый путь деривации из того же seed (§7.3.4).
5. **Device-ключи (вне протокола).** Транспортный уровень: тип схемы определяет транспорт (например, ключи libp2p / PeerId). Генерация — локальная случайная; device-ключ не выводится из seed. Сертификация: сертификат устройства $\mathrm{Cert} = \mathrm{Sig}_{human}(pk_{device},\ epoch,\ expiry)$ привязывает device-ключ к identity-ключу человека на срок. Привязка device → человек распространяется вне протокола двумя путями: (а) графовый — реестр устройств, подписанный identity-ключом список device-ключей с монотонным epoch, возится транспортом PoSoc как прикладная запись (payload), протокольной записью не являясь (§2.3); (б) точечный — устройство предъявляет сертификат при соединении. Отзыв устройства = новый epoch реестра без него. Механизмы сертификации и реестров — спецификация «transport-identity» экосистемы BeSoc; в протокол PoSoc device-ключи не входят.
6. **Канонизация:** детерминированный CBOR (§2.7–2.8).
7. **Объёмы записей:** `FRIEND` ≈ 200 Б; одиночные объекты/revoke ≈ 150 Б; `MEMBER_OF` ≈ 150 Б — 30 подтверждений ≈ 30 × 150 Б (подписная нагрузка та же, записи поштучно).
8. **Подписная нагрузка на человека в год** (специфицируемая часть — cadence TTL). Расчёт использует $N_{pop} = 10^9$, $\overline{|L0|} = 30$ и глубину иерархии $D = \log_2(10^9/30) \approx 25$. Ширина вершины равна 2 (§5.6.3, §9).

   В состав нагрузки входят ≈ 60 продлений `FRIEND`, 2 само-членства `MEMBER_OF`, ≈ 16 поштучных подтверждений `MEMBER_OF` (по $\lfloor |M|/2 \rfloor + 1$ при $|M| = 30$) и $2D \approx 50$ заявлений `MEMBER_OF` в сообщества. Итого получается ≈ **120–130 тихих записей/год**.

   Пропускная способность, политика relay и объём хранилищ — **вне спецификации** (implementation-defined; оценки — в сопроводительных материалах).

## 10. Ограничения и открытые вопросы

1. **Namespace:** имперсонация имён нерешаема; identity — структура.
2. **Многоличность:** принципиально не детектируется; смягчения — стоимость связей, эвристики.
3. **Публичность согласия:** видны составы и `MEMBER_OF`-заявления; приватизация — §11.
4. **Мажоритарная жёсткость:** индивидуум не привяжется без большинства своей L0.
5. **Сговор выше порогов:** выше $\kappa$ — вне гарантий.
6. **Спам:** структурно ограничен; остаточное — объёмы буферов.
7. **Грифинг ядом:** каскады сжимают окна. Взаимные marks (≤2 на пару) усиливают взаимный грифинг пары. Конечность меток и truce ограничивают этот эффект, но остаточный риск признан.
8. **Hijack и клиентские политики:** явные подтверждения операций; предупреждения о контрагентах с историей revoke.
9. **Цензура соседа:** сосед может утаивать записи. Anti-entropy и multi-parenting смягчают проблему, но единственный мост остаётся источником риска.
10. **Доступность данных:** prover может скрывать записи. Spot-check (§6.3) смягчает проблему, но скоординированное сокрытие остаётся риском.
11. **Дрейф порогов при росте:** рост брата повышает парный порог при неизменных связях. Это приводит к мгновенному detach и дорогому возврату ($T_{hold}$). Живучесть поддерживается через multi-parenting.
12. **Сложность вывода:** бинарность объединений (§5.5) делает парные проверки линейными по числу рёбер ($k \le 2$); обязательны индексы и инкрементальность.
13. **Консервативность rounds:** синхронное удаление не даёт максимальный roster. Это осознанный выбор: soundness важнее полноты.
14. **Расхождения часов:** влияют на мгновенные виды, но не на сходимость. $\Delta$ покрывает смещение часов.
15. **Управление параметрами:** изменение параметров означает форк. Governance не специфицирован.
16. **Squeeze-out (growth priority):** присоединение может вытеснить incumbents на пороге вплоть до quench. Враждебный join требует кворума подтверждений и разрушает также членство атакующего. Это осознанная цена детерминизма и отсутствия задержек.
17. **Транспортная инженерия:** relay-политика, пропускная способность, объёмы хранилищ — вне спецификации.

## 13. GLOSSARY

- **Нотация** — **G** — любая группа; **L0** — группа 0 уровня (базовая); **GH** — группа уровня выше L0 (иерархическое сообщество), идентификатор $ID_{GH}$; **P** — подписант записи (identity-ключ); **X** — любой identity-ключ; **O** (other) — любой identity-ключ, кроме подписанта. Правило стрелки: в `FRIEND_REVOKE(A→B)` подписант — $A$ (отзывающий), poison mark создаётся против $B$ (контрагента) (§3.2). Служебные обозначения: $S$ — bootstrap-множество, $H(\cdot)$ — функция хеширования (не путать с GH) (§2.1, §2.8).

**Identity & devices**

- **Ключ человека / identity-ключ** — единственный участник протокола PoSoc: пара $(x, pk)$ Ed25519, детерминированно выведенная из seed (§2.1, §8.4); только identity-ключи фигурируют в записях и подписывают их.
- **Ключ устройства / device-ключ** — транспортный ключ устройства (например, libp2p/PeerId), генерируемый локально случайно; вне протокола PoSoc: не фигурирует в записях и не подписывает их (§2.1.5, §8.5).
- **Сертификат устройства** — $\mathrm{Cert} = \mathrm{Sig}_{human}(pk_{device},\ epoch,\ expiry)$: подпись identity-ключа, привязывающая device-ключ к личности на срок; транспортный уровень, вне протокола (§8.5).
- **Реестр устройств** — подписанный identity-ключом список device-ключей владельца с монотонным epoch; возится транспортом PoSoc как прикладная запись (payload), протокольной записью не является (§8.5).
- **Epoch реестра** — монотонный номер версии реестра устройств: больший epoch замещает меньший; отзыв устройства — новый epoch без него (§8.5).
- **Seed** — мнемоническая фраза BIP-39 с опциональной passphrase, из которой KDF и деривация детерминированно выводят identity-ключ (§8.4, §9); модель stateless — восстановление личности = ввод seed на новом устройстве.
- **Passphrase** — опциональное «25-е слово», входящее в соль KDF вместе с мнемоникой; второй, отделяемый от фразы секрет (§8.4, §9).

**Records**

- **Consent object** — TTL-запись с автопродлением и мгновенным revoke; два типа: `FRIEND`, `MEMBER_OF` (§2.3).
- **Action** — запись с мгновенным эффектом, без TTL (§2.3).
- **`X_REVOKE`** — паттерн именования: action, отзывающий consent object типа X; подписант revoke совпадает с подписантом объекта (§2.3).
- **`FRIEND`** — consent object пары ключей; payload — каноническая пара $\{x, p\}$, $x < p$; подписи обеих сторон (§2.8, §3.1).
- **`FRIEND_REVOKE`** — односторонний разрыв: данные — та же каноническая пара; подписант — один из пары (отзывающий); прекращает instance и создаёт poison mark против контрагента — по правилу стрелки, против не-подписанта (§2.8, §3.2).
- **`KEY_LOSS`** — отзыв (смерть) ключа: action, подписант — сам ключ; все consent-записи ключа недействительны начиная с $t_{sign}$, новые недействительны по умолчанию; без poison marks и штрафов (§2.3).
- **`MEMBER_OF(X, G)`** — подтверждение членства «X member of G»: подписант = $X$ — само-членство (для сообществ $ID_{GH}$ — заявление о членстве, голос в C1-quorum); подписант ≠ $X$ — подтверждение другого (§4.2, §5.2).
- **`MEMBER_OF_REVOKE(X, G)`** — отзыв подтверждения членства: подписант $X$ — выход (для сообществ — отзыв заявления); подписант-подтверждающий — отзыв своего подтверждения; quorum отзывов = исключение (§4.2, §5.2).
- **`L0_GENESIS`** — адрес L0; без привилегий (§4.5).

**Time & state**

- **$t_{sign}$** — подписанное автором время записи; единственный источник времени (§2.4.1).
- **$now()$** — субъективные часы узла (§2.4.1).
- **Future rule / $\Delta$** — $t_{sign} > now+\Delta$: discard с пере-оценкой; в коридоре: deferred (§2.4.2).
- **LWW** — для записей одного назначения действует max $t_{sign}$; замещение при строго большем; равные → меньший $H(\mathrm{record})$ (§2.4.4).
- **Designation** — identity записи для конфликтов: тип + ключевые поля (для парных — включая направление) (§2.4.4).
- **Reconstruction** — нормативное вычисление: сортировка по $(t_{sign}, H(\mathrm{record}))$, последовательное применение (§2.4.6).
- **Stored record set** — хранимое множество записей; аргумент функции состояния (§2.4.8).
- **Re-publish** — повторная публикация живых `MEMBER_OF` при изменении membership-статуса (§2.4.9).

**Links**

- **Instance** — текущий `FRIEND` пары; замещается более свежим (§3.1).
- **Binding** — привязка `FRIEND_REVOKE` к последнему instance с $t_c \le t_{sign}$ (§3.2.2).
- **Winning revoke** — действующий revoke направления: max $t_{sign}$ на instance (§3.2.3).
- **Mutual revoke** — revoke обоих направлений одной пары; не конфликтуют; обе стороны помечены (§3.2.3).
- **Poison mark** — активна на $[t_b, \min(t_c+T_{life}, t_{relink}))$; ≤1 на пару-направление, ≤2 на пару (§3.2.4).
- **Clamp** — $t_b = \min(t_{sign},\ t_c + T_{life})$: разрыв зажат в базовое окно instance (§3.2.4).
- **$N_X$** — число активных marks против $X$; $N_X \le \deg(X)$ (§3.2).
- **Window / decay** — $W = T_{life}/(1+N_P+N_O)$; $d(\ell)$ — момент распада; необратимость — относительно текущего множества записей (§3.3).
- **Truce** — свежий `FRIEND` пары: усекает marks обоих направлений, расширяет окна выживающих связей (§3.2, св. 3).
- **GC horizon** — записи пары хранятся до $t_{last}+2T_{life}$; дальше — не влияют ни на что (§2.2.5, §3.4.1).

**L0**

- **Candidate** — identity-ключ с живым само-членством `MEMBER_OF` (§4.3.1).
- **Materialization** — вхождение кандидата в активный roster (§4.4).
- **Active member** — участник, прошедший rounds (§4.3).
- **Кворум подтверждений (member-of-quorum)** — $\lfloor |M|/2 \rfloor + 1$ живых `MEMBER_OF` от текущих членов (§4.3.4a).
- **Cohesion** — $\lfloor |M|/2 \rfloor + 1$ активных связей с активными членами (§4.3.4b).
- **Synchronous rounds** — одновременное удаление нарушителей до фикс-точки; sound, не maximal (§4.3.4).
- **Growth priority** — начальный roster = все кандидаты; присоединение никогда не блокируется (§4.3.3).
- **Squeeze-out** — вытеснение incumbents укрупнёнными порогами; принятая семантика (§4.3.3, §10.16).
- **Cap-30** — отбор кандидатов: счёт подтверждений → $t_{sign}$ → pk (§4.3.2).
- **Freshness tie-break** — равные притязания → fresher $t_{sign}$ (§4.3.5).
- **Quench** — $|M_{act}| < 4$: roster пуст, edges отваливаются каскадом (§4.3.6).

**Hierarchy**

- **Isolate** — 0 живых детей; $R_{str} = \varnothing$; привязывается только bootstrap (§5.5, §5.6.2).
- **Vertex** — 2 живых ребёнка — предел бинарности (§5.5).
- **Free group** — 1 живой ребёнок; edge грандфатерится; общие правила (§5.5, §5.6.2).
- **Edge / child / parent / sister** — привязка $G \to GH$; $G$ — child, $GH$ — parent; другие дети $GH$ — sisters (§5.5).
- **C1** — quorum живых `MEMBER_OF(P, GH)` (§5.5).
- **C2 (corroboration)** — пара с единственной живой сестрой; детей у сообщества ≤ 2 (§5.5).
- **C3** — acyclicity (§5.5).
- **Hold window ($T_{hold}$)** — непрерывное выполнение условий перед активацией (§5.5).
- **Freeze ($T_f$)** — блокировка новых активаций вверх после `L0_GENESIS` и bootstrap; параллелен hold window (§5.5).
- **Bootstrap / S-set** — совместная активация ровно 2 рёбер к пустой группе (бинарность); все пары внутри $S$; окно на фиксированном $S$; выбор: ранний старт → лексикографический минимум (§5.5).
- **Attach / detach** — присоединение к живой группе / мгновенный отрыв (провал C1 или любой пары — оба edge) (§5.5–5.6).
- **Demotion** — vertex → free group (1 ребёнок) → isolate (0) с отвалом восходящих edges тем же пересчётом (§5.6.2).
- **Grandfathered edge** — edge свободной группы, сохранённый при понижении (§5.6.2).
- **$R_{str}$ / $R_{decl}$** — структурный roster (союз живых детей; задаёт численности) / roster заявлений `MEMBER_OF(P, GH)` (не носитель доверия) (§5.3).
- **Level ($L$)** — $1 + \max$ по живым детям; метаданные (§5.6.3).
- **Multi-parenting** — группа — ребёнок любого числа родителей; штатное состояние DAG (§5.6.4).
- **Disjoint count ($U$)** — corroboration только во внешнюю часть контрагента (§5.4.1).
- **$f$-curve / $\gamma$ / $\kappa$ (conspiracy floor)** — пороговая арифметика пар (§5.4.2).

**Network**

- **Узел** — устройство человека, действующее от имени identity-ключа владельца (§2.2.1).
- **Neighbor** — соседство людей: у людей $U$ и $V$ есть активная `FRIEND`; сетевые соединения устанавливаются между их device-ключами по правилу маппинга §2.2.1; транспорт совпадает с графом доверения на уровне людей.
- **Sync queue** — исходящий буфер ретрансляции (§2.2).
- **Anti-entropy** — периодическая сверка множеств записей; подавляет цензуру и потери (§2.2.3).
- **Mandatory zone** — свои связи и группы; глубже — политика узла (§2.2.4).
- **Relevance** — политика хранения/ретрансляции, не валидности (§2.6.1).
- **Caps / rate-limit** — детерминированные лимиты живых объектов и обновлений на identity-ключ (§2.6).

**Trust**

- **Proof (subtree)** — все дети каждого parent на пути + перекрёстные связи (C2) + численности (§6.1).
- **Spot-check** — опрос $k$ случайных участников rosters о записях, затрагивающих proof; расхождение → reject; SHOULD (§6.3).
- **Trusted set** — транзитивное замыкание родителей L0 верификатора + его политика (§6.2).
- **Inclusion cost** — $\approx t$ взаимных живых связей, рекуррентно $\le T_{life}$ (§1.3).
- **Hijack localization** — сжатие окон в $1+N$; чужие marks нестерираемы; против подделки задним числом — `KEY_LOSS` (§7.3, §2.3).
