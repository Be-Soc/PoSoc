# Реализация протокола PoSoc

Реализационная часть: конкретные средства, форматы сообщений, криптография, транспорт и узловая механика.

> ARCH-2.2.x-impl и ARCH-2.5 размещены в implementation.md по решению владельца.

## 2.2 Объекты узла

<a id="arch-2.2-impl"></a>

**Объекты узла:** БД состояния (живые записи + ретроспективный буфер), sync queue.

### 2.2.1 Транспорт как социальный граф

<a id="arch-2.2.1"></a>

1. **Транспорт = социальный граф.** Запись ретранслируется только узлам с активной `FRIEND`. Компонент связности является изолированной вселенной данных: записи человеческого компонента физически не достигают бот-кластеров. Это даёт двойную изоляцию — структурную и транспортную. Свежий ключ без связей не получает трафика; установление `FRIEND` включает слив состояния.

### 2.2.2 Обработка записи

<a id="arch-2.2.2-impl"></a>

2. **Обработка записи:** узел проверяет подписи, каноническую форму и применимость записи ([ARCH-2.4.8](concept.md#arch-2.4.8)); затем применяет запись к БД, ставит её в sync queue и рассылает соседям.

### 2.2.3 Anti-entropy

3. **Anti-entropy.** <a id="arch-2.2.3"></a>Утаивание записей соседом обнаруживается сверкой через других соседей; риск единственного моста остаётся ограничением ([LIM-10.9](concept.md#lim-10.9)). <a id="arch-2.2.3-impl"></a>Узел периодически сверяет множества записей с каждым соседом по диапазонам времени и хешам, после чего подтягивает расхождения.

### 2.2.4 Обязательная зона хранения

<a id="arch-2.2.4"></a>

4. **Обязательная зона хранения:** записи собственных связей и групп. Глубина остального — политика узла; правила relay и пропускная способность — **вне спецификации** (implementation-defined).

### 2.2.5 GC-горизонты

<a id="arch-2.2.5"></a>

5. **GC horizons (минимум для корректности собственного состояния):** записи пары — до $t_{last} + 2T_{life}$ ($t_{last}$ — позднейшая $t_{sign}$ пары; лемма [LINK-3.4.1](concept.md#link-3.4.1)); consent objects — до конца эффекта; `KEY_LOSS` — до истечения TTL самой долгоживущей записи ключа на момент $t_{sign}$ отзыва ([ARCH-2.3.2](concept.md#arch-2.3.2)); L0_GENESIS / адреса групп — хранятся владельцем адреса и любым узлом по политике.

## 2.5 Синхронизация и сходимость

<a id="arch-2.5"></a>Согласованность достигается в пределе, но в каждый конкретный момент узлы могут иметь субъективно разные состояния. Потребитель доверия всегда читает текущее состояние своей реплики. Цензура соседа подавляет доставку, но не искажает семантику: задержанная запись применяется со своей $t_{sign}$. <a id="arch-2.5-impl"></a>Gossip выполняется при появлении записи, а anti-entropy — по расписанию.

Разделы 2.7 и 2.8 задают машинное представление записей. Смысл записей и правила их применения описаны в концептуальной части спецификации.

## 2.7 Канонизация

<a id="fmt-2.7"></a>

Канонический CBOR (ключи отсортированы); пары ключей лексикографически; самосвязи запрещены; $H$ — BLAKE3; округления порогов — $\lfloor x + 10^{-9} \rfloor$.

## 2.8 Форматы записей (норматив)

<a id="fmt-2.8"></a>

Record = `{type, t_sign, payload, sigs}`; sigs — массив `{pk, sig}`, **отсортированный по pk**. Signing payload = канонический CBOR `{type, t_sign, payload}` — каждый подписант подписывает одни и те же байты. Идентичность записи = $H(\mathrm{record})$ (полные канонические байты); дедупликация по содержимому.

| type | payload | sigs |
|---|---|---|
| `FRIEND` | `{x: pk, p: pk}` ($x < p$) | `[x, p]` |
| `FRIEND_REVOKE` | `{x: pk, p: pk, memo?: bstr ≤ 256}` (O→P) | `[x]` |
| `MEMBER_OF` / `MEMBER_OF_REVOKE` | `{group: ID, member: pk}` | `[signer]` |
| `L0_GENESIS` | `{descriptor: tstr ≤ 128, initiator: pk}` | `[initiator]` |
| `KEY_LOSS` | `{memo?: bstr ≤ 256}` | `[self]` |

`MEMBER_OF` читается как «X member of G». Поле `member` задаёт члена $X$. Если подписантом является $X$, это само-членство; для сообщества оно является заявлением о членстве, а его revoke — выходом или отзывом заявления. Если подписант не равен $X$, это подтверждение другого участника; его revoke — отзыв подтверждения. Подписант не дублируется в `payload`: он определяется подписью в `sigs`, как стороны `FRIEND` определяются полями `x` и `p`, а подписанты — массивом `sigs`.

Идентификаторы групп вычисляются из содержимого и не требуют реестра:

- $ID_G = H(\texttt{"L0"} \Vert \text{descriptor} \Vert pk_{initiator} \Vert t_{sign})$ — идентификатор базовой группы L0;
- $ID_{GH} = H(\texttt{"GROUP"} \Vert \text{descriptor} \Vert pk_{founder})$ — идентификатор сообщества иерархии.

Здесь founder — `pk` первой по $t_{sign}$ записи `MEMBER_OF` с `group: ID_GH`. Это техническая роль без привилегий. Поле `group` содержит $ID_G$ для L0 ([L0-4](concept.md#l0-4)) и $ID_{GH}$ для сообщества ([HIER-5.2](concept.md#hier-5.2)); типы идентификаторов различаются доменным тегом хеша. Доменное разделение BLAKE3 выполняется по тегам типов, а tie-break $H(\mathrm{record})$ вычисляется от полных канонических байтов. В `KEY_LOSS` отзываемый ключ — единственный подписант (`self`); идентифицирующих полей в `payload` нет ([ARCH-2.3.2](concept.md#arch-2.3.2)).

## 8. Криптография и объёмы

<a id="crypto-8"></a>

<a id="crypto-8.7"></a>

**[CRYPTO-8.7]** Схемы этого раздела — конкретизация абстрактных требований concept (подпись, детерминированное хеширование, каноническая сериализация); сам concept от конкретных примитивов не зависит. Замена примитивов допустима при сохранении абстрактных свойств: невозможность подделки подписи, коллизионная устойчивость хеширования, детерминированность канонизации; такое изменение — форк параметров ([LIM-10.15](concept.md#lim-10.15)).

<a id="crypto-8.1"></a>

1. **Подписи:** Ed25519 (pk 32 Б, sig 64 Б); интерфейс допускает постквантовые схемы.

<a id="crypto-8.2"></a>

2. **Хеши:** BLAKE3, доменное разделение по типам записей ([FMT-2.8](#fmt-2.8)).

<a id="crypto-8.3"></a>

3. **Канал уведомлений (опционально):** $s_{uv} = \mathrm{HKDF}(\mathrm{X25519}(x_u, pk_v))$ — координация продлений и подписей `FRIEND`; не источник истины.

<a id="crypto-8.4"></a>

4. **Канонизация:** детерминированный CBOR ([FMT-2.7](#fmt-2.7)–[FMT-2.8](#fmt-2.8)).

<a id="crypto-8.5"></a>

5. **Объёмы записей:** `FRIEND` ≈ 200 Б; одиночные объекты/revoke ≈ 150 Б; `MEMBER_OF` ≈ 150 Б — 30 подтверждений ≈ 30 × 150 Б (подписная нагрузка та же, записи поштучно).

<a id="crypto-8.6"></a>

6. **Подписная нагрузка на человека в год** (специфицируемая часть — cadence TTL): ≈ 60 продлений `FRIEND` + 2 само-членства `MEMBER_OF` + подтверждения членов поштучно (`MEMBER_OF`) + ~$2D \approx 16\text{–}20$ заявлений `MEMBER_OF` в сообщества ≈ **80–100 тихих записей/год** (нагрузка прежняя — подтверждение каждого члена подписывается так же, только записями поштучно). Пропускная способность, политика relay и объём хранилищ — **вне спецификации** (implementation-defined; оценки — в сопроводительных материалах).

## 12. Эталонные реализации

<a id="ref-12"></a>

<a id="ref-12.1"></a>

Спецификация нормативна, а реализации v0.11 — **отдельный артефакт**. Эталонная реализация должна включать следующие компоненты:

1. **Реконструкция пары:** binding, выбор максимального $t_{sign}$ отдельно для каждого направления, кламп и truce ([LINK-3.2](concept.md#link-3.2)).
2. **Ростер L0:** cap, growth priority и синхронные раунды фильтрации ([L0-4.3](concept.md#l0-4.3)).
3. **Вывод рёбер:** all-pairs C2, acyclicity C3, hold window, S-bootstrap и freeze ∥ window ([HIER-5.5](concept.md#hier-5.5)–[HIER-5.6](concept.md#hier-5.6)).
