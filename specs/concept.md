# Спецификация протокола PoSoc (v0.13)

Концептуальная часть: назначение, семантика, математика и гарантии протокола.

## 1. Назначение, принципы, модель угроз

<a id="prin-1"></a>

### 1.1 Назначение

<a id="prin-1.1"></a>

Цель — децентрализованная сеть доверия (**PoSoc — Proof of Social**), позволяющая каждому участнику отличать реальных людей от ботов/виртуальных аккаунтов **в пределах наблюдаемого им компонента социального графа**. Гарантии — условные и вероятностные, в терминах стоимости атаки.

### 1.2 Принципы

<a id="prin-1.2"></a>

<a id="prin-1.2.1"></a>

1. **Отсутствие инфраструктуры.** Нет корневых узлов, валидаторов, ledger, субстрата упорядочивания. Сеть — участники и их связи.

<a id="prin-1.2.2"></a>

2. **Одноранговость.** Полномочий нет; каждый валидирует состояние сам.

<a id="prin-1.2.3"></a>

3. **Субъективное локальное доверие.** Участник доверяет иерархиям, достижимым из его L0 ([TRUST-6](#trust-6)).

<a id="prin-1.2.4"></a>

4. **Стоимость вместо альтруизма.** Протокол не предполагает честности: подтверждение ботов — стоимостно и рекуррентно. Подкуп и обман — векторы стоимости ([PRIN-1.3](#prin-1.3)).

<a id="prin-1.2.5"></a>

5. **Публичность внутри компонента.** Записи публичны в компоненте связности; валидность — чистая функция данных.

<a id="prin-1.2.6"></a>

6. **Эфемерность.** Все факты — автопродлеваемые TTL-объекты с мгновенным revoke; «купленного» факта не существует.

<a id="prin-1.2.7"></a>

7. **Взаимность согласия.** Вход двусторонен (обе подписи / quorum); revoke и выход — односторонни. Молчаливого согласия нет.

<a id="prin-1.2.8"></a>

8. **Эмерджентность иерархии.** Edges и levels — выводимое состояние, не записи.

<a id="prin-1.2.9"></a>

9. **Время подписи.** Состояние — функция множества подписанных записей и текущего времени; порядок доставки семантики не имеет.

<a id="prin-1.2.10"></a>

10. **Единая семантика revoke.** Каждый consent object X отзывается действием `X_REVOKE` того же подписанта; свежая подпись всегда сильнее старой.

### 1.3 Модель угроз

<a id="prin-1.3"></a>

<a id="prin-1.3.1"></a>

**Противник может** создавать неограниченно ключей (Sybil) и контролировать связи своих узлов. Он может создавать группы и MEMBER_OF-заявления (permissionless), получать связи с людьми (встреча, обман, подкуп), похищать ключи, бэйдейтить $t_{sign}$ собственных записей, задерживать или утаивать записи при ретрансляции, а также смещать собственные часы. Если противник контролирует ключ, он может опубликовать его отзыв ([ARCH-2.3.2](#arch-2.3.2)) и уничтожить личность.

<a id="prin-1.3.2"></a>

**Противник не может (криптографически)** подделать подпись, создать или продлить consent object без требуемых подписей, а также включить участника в L0 без его подписи. Он не может отозвать чужой consent object. Он также не может отозвать чужой ключ без владения его секретом, аннулировать poison mark без подписи создавшей стороны или fresh FRIEND пары, а также привязать группу к иерархии без живых внешних связей и quorum заявлений `MEMBER_OF`.

<a id="prin-1.3.3"></a>

**Гарантии (в пределах допущений):**

<a id="prin-1.3.3-a"></a>

- *Inclusion cost:* включение бот-компонента в человеческую иерархию требует $\approx t$ взаимных живых связей; линейно по порогу, рекуррентно ($\le T_{life}$).

<a id="prin-1.3.3-b"></a>

- *Isolation:* MEMBER_OF-заявления без внешних живых связей не создают edges (disjoint count, [HIER-5.4](#hier-5.4)); транспортная изоляция дублирует структурную ([ARCH-2.2](#arch-2.2)).

<a id="prin-1.3.3-c"></a>

- *Backdating containment:* подделку задним числом устраняет `KEY_LOSS` — смерть ключа гасит все его записи, включая поддельные; без `KEY_LOSS` подделка необратима (принятая цена) ([LINK-3.2](#link-3.2), [ARCH-2.3.2](#arch-2.3.2)).

<a id="prin-1.3.3-d"></a>

- *Hijack localization:* окна сжимаются в $1+N$ раз; чужие marks угонщик не стирает; исключение — quorum отзывов, мгновенно.

<a id="prin-1.3.4"></a>

**Негарантии:** многоличность ([LIM-10.2](#lim-10.2)); сговор выше порогов ([LIM-10.5](#lim-10.5)); приватность ([ZKP-11](#zkp-11)); мгновенная глобальная согласованность ([ARCH-2.5](implementation.md#arch-2.5)); гарантированная доставка ([LIM-10.9](#lim-10.9)–[LIM-10.10](#lim-10.10)); уничтожение личности угонщиком — контролируемый ключ может отозвать сам себя (восстановление — ротация, [DEF-7.3.3](#def-7.3.3)).

## 2. Архитектура

<a id="arch-2"></a>

### 2.1 Identity

<a id="arch-2.1"></a>

<a id="arch-2.1.1"></a>

1. Личность — пара ключей $(x, pk)$ (подписывающий секрет $x$ не публикуется; конкретная схема подписи — деталь реализации, [CRYPTO-8](implementation.md#crypto-8)).

<a id="arch-2.1.2"></a>

2. Регистрации нет: ключ существует, если фигурирует в живой записи. Sybil-устойчивость — граф, не реестр.

<a id="arch-2.1.3"></a>

3. Один человек может владеть несколькими ключами ([LIM-10.2](#lim-10.2)); перенос истории протоколом не гарантируется ([DEF-7.3.3](#def-7.3.3)).

<a id="arch-2.1.4"></a>

4. Отозванный ключ не существует: `KEY_LOSS` ([ARCH-2.3.2](#arch-2.3.2)) делает все записи ключа невалидными от своей $t_{sign}$; записи ключа с большей $t_{sign}$ невалидны по умолчанию — несуществующий ключ не может давать согласие. Правило [ARCH-2.1.2](#arch-2.1.2) не «оживляет» ключ через его собственную запись отзыва.

### 2.2 Сеть без ledger

<a id="arch-2.2"></a>

2. Механика обработки записи на узле — [ARCH-2.2.2-impl](implementation.md#arch-2.2.2-impl) (implementation).

3. Anti-entropy: механика и гарантия обнаружения утаивания — [ARCH-2.2.3](implementation.md#arch-2.2.3) (implementation).

4. Обязательная зона хранения — [ARCH-2.2.4](implementation.md#arch-2.2.4) (implementation).

5. GC horizons (минимум для корректности собственного состояния) — [ARCH-2.2.5](implementation.md#arch-2.2.5) (implementation).

### 2.3 Записи

<a id="arch-2.3"></a>

Записи канонизируются детерминированной сериализацией ([FMT-2.7](implementation.md#fmt-2.7)); $t_{sign}$ входит в подписываемую полезную нагрузку. Два класса: **consent objects** (TTL, автопродление, revoke; два типа: `FRIEND`, `MEMBER_OF`) и **actions** (мгновенный эффект).

| Record | Signers | Класс | Эффект |
|---|---|---|---|
| `FRIEND(O, P)` | $P$ и $O$ | object, $T_{life}$ | friend instance пары ([LINK-3](#link-3)) |
| `FRIEND_REVOKE(O→P, memo?)` | $O$ | action | terminирует instance + poison mark ([LINK-3.2](#link-3.2)) |
| `MEMBER_OF(X,G)` | подписант $P$: $P=X$ — само-членство, $P \ne X$ — подтверждение | object, $T_{life}$ | членство «X member of G»: L0 и заявления в сообщества ([L0-4](#l0-4), [HIER-5.2](#hier-5.2)) |
| `MEMBER_OF_REVOKE(X,G)` | подписант $P$: $P=X$ — выход, $P \ne X$ — подтверждающий | action | отзыв подтверждения: выход $X$ или отзыв чужого подтверждения ([L0-4.2](#l0-4.2)) |
| `L0_GENESIS(P, descriptor)` | $P$ (инициатор) | action | адрес L0 ([L0-4.5](#l0-4.5)) |
| `KEY_LOSS(memo?)` | $P$ (сам ключ) | action | смерть ключа: инвалидация всех записей ключа ([ARCH-2.3.2](#arch-2.3.2)) |

`MEMBER_OF(X,G)` — единый тип членства, читается «X member of G»: подписант $P$: $P=X$ — само-членство (для $ID_{GH}$ — заявление о членстве в сообществе); $P \ne X$ — подтверждение члена другим участником (quorum-правило мгновенного исключения для чужих подтверждений — [L0-4.2](#l0-4.2)). Различение сценариев — по типу ID группы: $ID_G$ — базовая группа L0 ([L0-4](#l0-4)); $ID_{GH}$ — сообщество иерархии: живые `MEMBER_OF(P,GH)` образуют $R_{decl}(GH)$ и голосуют в C1-quorum ([HIER-5.2](#hier-5.2)).

<a id="arch-2.3.1"></a>

**Номенклатура `X_REVOKE`:** X — тип отзываемого consent object; подписант revoke совпадает с подписантом объекта. Событий слияний, вето, якорей, версий составов не существует.

<a id="arch-2.3.2"></a>

**`KEY_LOSS` — смерть ключа.** Это action; подписант — сам ключ (`[self]`, [FMT-2.8](implementation.md#fmt-2.8)). Назначение — тип + подписант; экземпляр на ключ один: второй `KEY_LOSS` того же подписанта игнорируется по общим правилам LWW ([ARCH-2.4.4](#arch-2.4.4)).

Эффект от $t_{sign}$ записи: все consent-записи ключа — `FRIEND` (в обе стороны) и `MEMBER_OF`, включая живые instance (экземпляры связи), — невалидны; consent-записи ключа с большей $t_{sign}$ невалидны по умолчанию ([ARCH-2.1.4](#arch-2.1.4)). Ключ прекращает существование.

Для `FRIEND` с участием отозванного ключа instance терминирован. Вторая сторона жива, её записи валидны, её перелинковка с новым ключом владельца — обычная связь ([LINK-3.1](#link-3.1)).

Штрафов нет: `KEY_LOSS` не создаёт poison marks и не влияет на окна/decay — созданные ключом `FRIEND_REVOKE` и метки против ключа сохраняют эффект (отмывание недоступно, [LINK-3.2.9](#link-3.2.9)); `break` — это `FRIEND_REVOKE` ([LINK-3.2](#link-3.2)), а не `KEY_LOSS`.

Roster L0 и C1-кворумы пересчитываются существующими механизмами — мгновенный каскад ([L0-4.3](#l0-4.3), [HIER-5.6](#hier-5.6)).

Живость записи `KEY_LOSS` — не меньше TTL самой долгоживущей записи ключа на момент $t_{sign}$ отзыва. После истечения всех записей ключа его существование ничем не поддерживается; GC-горизонт — [ARCH-2.2.5](implementation.md#arch-2.2.5).

### 2.4 Время, конфликты, revoke-семантика, детерминизм

<a id="arch-2.4"></a>

<a id="arch-2.4.1"></a>

1. **$t_{sign}$** — заявленное автором время, подписано. **$now()$** — локальные часы узла. Состояние вычисляется «на момент» $\tau$.

<a id="arch-2.4.2"></a>

2. **Правило будущего.** $t_{sign} > now + \Delta$ ($\Delta = 7$ сут.) — запись отбрасывается и пере-оценивается при повторной доставке (часы могли догнать). $t_{sign} \in (now,\ now+\Delta]$ — хранится и ретранслируется, к состоянию не применяется до догонa часов.

<a id="arch-2.4.3"></a>

3. **Прошлое не ограничено.** Поздняя публикация принимается; ретроспективные эффекты ограничены горизонтами объектов ([LINK-3.4.1](#link-3.4.1)).

<a id="arch-2.4.4"></a>

4. **Разрешение конфликтов (LWW).** Для записей одного **назначения** (identity: тип + все ключевые поля, включая направление для парных записей) действует запись с максимальным $t_{sign}$. Замещение — только при **строго большем** $t_{sign}$; при равенстве — запись с **меньшим** $H(\mathrm{record})$, вторая игнорируется. Единое правило для объектов и действий.

<a id="arch-2.4.5"></a>

5. **Revoke-семантика (общая).** `X_REVOKE` обрезает живость соответствующих объектов **вперёд** от своей $t_{sign}$: уничтожаются объекты того же назначения с $t_{sign} \le t_{sign}(\mathrm{revoke})$; объекты с большей $t_{sign}$ — свежее согласие, выживают. `X_REVOKE` покрывает consent objects; смерть ключа — отдельный механизм `KEY_LOSS` ([ARCH-2.3.2](#arch-2.3.2)). Специфика `FRIEND_REVOKE` (binding, poison) — [LINK-3.2](#link-3.2).

<a id="arch-2.4.6"></a>

6. **Reconstruction.** Норматив — полная реконструкция: записи сортируются по $(t_{sign},\ H(\mathrm{record}))$ и применяются последовательно. Результат не зависит от порядка получения записей узлом. Инкрементальные вычисления допустимы при совпадении результата.

<a id="arch-2.4.7"></a>

7. **Живость consent object на $\tau$:** $t_{sign} \le \tau < t_{sign}+T_{life}$ ∧ не отозван ([ARCH-2.4.5](#arch-2.4.5)) ∧ ключ-подписант не отозван ([ARCH-2.3.2](#arch-2.3.2)).

<a id="arch-2.4.8"></a>

8. **Определение состояния.** Состояние = чистая функция (**хранимого** множества записей, $\tau$). Транзиторное неравенство хранимых множеств между узлами — норма; сходимость — [ARCH-2.5](implementation.md#arch-2.5). Правила игнорирования (детерминированные): неверная подпись; неканоническая форма; $t_{sign} > now+\Delta$; неприменимость (`FRIEND_REVOKE` без bound instance — [LINK-3.2](#link-3.2); revoke объекта, которого нет в БД); записи отозванного ключа с $t_{sign} > t_{sign}(\mathrm{KEY\_LOSS})$ ([ARCH-2.3.2](#arch-2.3.2)). Капы [ARCH-2.6.2](#arch-2.6.2) и rate-limit [ARCH-2.6.3](#arch-2.6.3) — правила **отбора и замещения на уровне состояния**, не валидации: «лишние» записи хранятся, но не считаются.

<a id="arch-2.4.9"></a>

9. **Re-publish.** При изменении membership-статуса ключа (вступление в живую группу) узел повторно публикует свои живые `MEMBER_OF` (relevance — политика хранения/ретрансляции, не валидности).

### 2.5 Синхронизация и сходимость

Модель доставки и сходимости (gossip, anti-entropy, согласованность в пределе) — [ARCH-2.5](implementation.md#arch-2.5) (implementation).

### 2.6 Antispam (структурный)

<a id="arch-2.6"></a>

<a id="arch-2.6.1"></a>

1. **Relevance:** хранятся и ретранслируются записи, влияющие на состояние (`MEMBER_OF(P,GH)` от ключей $P$ вне живых $R_{str}(GH)$ не хранятся; re-publish — [ARCH-2.4.9](#arch-2.4.9)).

<a id="arch-2.6.2"></a>

2. **Капы живых объектов на ключ (уровень состояния):** ≤ 128 живых `MEMBER_OF` на ключ — суммарно: L0-членства и заявления в сообщества (сверх — считаются 128 с наибольшими $t_{sign}$, тай-брейк по $H$); `FRIEND` и `MEMBER_OF_REVOKE` капом не ограничены. Правило подсчёта подтверждений: в кворумы входят только `MEMBER_OF` от текущих членов соответствующего $R_{str}$ (для L0 — [L0-4.3.4-a](#l0-4.3.4-a)); подтверждение от не-члена хранится, не считается.

<a id="arch-2.6.3"></a>

3. **Rate-limit:** обновление объекта с $t_{sign}' < t_{sign} + 7$ сут. не замещает прежнее.

## 3. Связи

<a id="link-3"></a>

### 3.1 Instances

<a id="link-3.1"></a>

1. <a id="link-3.1.1"></a>Связь — отношение пары ключей; у пары существует не более одного текущего instance (экземпляра связи).
2. <a id="link-3.1.2"></a>`FRIEND(O, P)` с $t_c = t_{sign}$ создаёт instance; instance с большей $t_c$ замещает прежний (архив); метки пары усекаются ([LINK-3.2.4](#link-3.2.4)).
3. <a id="link-3.1.3"></a>Активная связь на $\tau$: instance не терминирован и не распался.

### 3.2 `FRIEND_REVOKE` и poison mark

<a id="link-3.2"></a>

**Реконструкция пары $(O, P)$** выполняется в следующем порядке:

1. <a id="link-3.2.1"></a>**Instances:** записи `FRIEND` упорядочиваются по $t_c$ (тай-брейк — меньший $H$).
2. <a id="link-3.2.2"></a>**Binding:** `FRIEND_REVOKE(O→P)` с $t_{sign}=s$ привязывается к instance $\ell$ = последнему `FRIEND` пары с $t_c \le s$. Если такого instance нет, запись игнорируется.
3. <a id="link-3.2.3"></a>**Разрешение по направлениям.** Записи направлений $O \to P$ и $P \to O$ **независимы и не конфликтуют** (взаимный revoke законен: каждая сторона отзывает своё согласие). Внутри одного направления, привязанного к $\ell$, действует запись с **максимальным** $t_{sign}$ (тай-брейк — меньший $H$); прочие игнорируются.
4. <a id="link-3.2.4"></a>**Эффект действующего `FRIEND_REVOKE(O→P, s)`** на instance $\ell$:
   - <a id="link-3.2.4-a"></a>$t_b = \mathrm{clamp}(s,\ t_c(\ell),\ t_c(\ell)+T_{life}) = \min(s,\ t_c(\ell)+T_{life})$ (binding даёт $s \ge t_c$);
   - <a id="link-3.2.4-b"></a>$\ell$ **terminируется** в $t_b$ (при нескольких действующих revoke — в наименьшем $t_b$);
   - <a id="link-3.2.4-c"></a>**poison mark против $P$:** активен на $[\,t_b,\ \min(t_c(\ell)+T_{life},\ t_{relink})\,)$, где $t_{relink}$ — $t_c$ следующего `FRIEND` пары (нет — $\infty$).
   - <a id="link-3.2.4-d"></a>При $s > t_c(\ell) + T_{life}$: интервал пуст — terminация без mark.
5. <a id="link-3.2.5"></a>**Пункт упразднён (v0.13).** Механизм встречного отзыва удалён: точечного средства против подделки задним числом нет, пока ключ жив; средство — `KEY_LOSS` ([ARCH-2.3.2](#arch-2.3.2)) — смерть ключа гасит все его записи, включая поддельные.

**Свойства.** Из правил реконструкции следуют свойства отзыва и меток:

1. <a id="link-3.2.6"></a>**Направленность:** mark создаётся против контрагента отзывающего («травится покинутый»). **Взаимные revoke → обе стороны помечены.**
2. <a id="link-3.2.7"></a>**≤ 1 mark на пару-направление, ≤ 2 на пару.** Метки разных пар стекируются; $N_X \le \deg(X)$ — инвариант сохраняется.
3. <a id="link-3.2.8"></a>**Truce.** `FRIEND(O, P)` усекает метки **обоих направлений** пары; окна выживающих связей $O$ и $P$ расширяются немедленно; метки третьих лиц не затрагиваются.
4. <a id="link-3.2.9"></a>**Отмывание недоступно.** Аннулирование mark требует fresh `FRIEND` пары (подписи обеих сторон, включая отзывавшего). Угонщик не стирает метки друзей жертвы; подделку задним числом устраняет только `KEY_LOSS` — смерть ключа гасит все его записи, включая поддельные ([ARCH-2.3.2](#arch-2.3.2)).
5. <a id="link-3.2.10"></a>**Цена грифинга.** Цикл `FRIEND↔FRIEND_REVOKE` требует подписи «жертвы» на каждый `FRIEND`; собственные метки пары не накапливаются (≤2).
6. <a id="link-3.2.11"></a>**Каскад revoke** против одного ключа — публичный сигнал компрометации ([DEF-7.4](#def-7.4)).

### 3.3 Decay

<a id="link-3.3"></a>

$$W_\ell(\tau) = \frac{T_{life}}{1+N_P(\tau)+N_O(\tau)},\qquad d(\ell)=\min\{\tau \ge t_c:\ \tau - t_c \ge W_\ell(\tau)\}$$

1. <a id="link-3.3.1"></a>$W$ кусочно-постоянна; $d(\ell)$ — сканирование моментов начала/конца меток против $P$ и $O$. Распад не позднее $t_c + T_{life}$.
2. <a id="link-3.3.2"></a>Активность $\ell = [t_c,\ \min(d(\ell),\ t_b))$.
3. <a id="link-3.3.3"></a>**Необратимость — относительно текущего множества записей:** расширение окон отодвигает распад выжившего, но не оживляет распавшийся; позднее прибытие записи может переписать историю пары (осознанное следствие «прошлое не ограничено», [ARCH-2.4.3](#arch-2.4.3)). Оживление пары — только её новый `FRIEND`.

### 3.4 Леммы и пример

<a id="link-3.4"></a>

1. <a id="link-3.4.1"></a>**GC horizon.** Mark не создаёт эффектов позже $t_c(\ell) + 2T_{life}$: сам живёт $\le t_c + T_{life}$ и влияет на окна связей, созданных не позже чем на $T_{life}$ позже.
2. <a id="link-3.4.2"></a>Все производные величины вычисляются из хранимого множества записей без истории применения.

*Пример* ($T_{life}=12$ мес., проверен): revoke $(P_1, O_1)$ в $t{=}2$ (instance $t_c{=}0$) → mark $[2,12)$ против $O_1$; связь $(O_1, X_2)$ ($t_c{=}0$): окно 6 мес., распад $t{=}6$; truce `FRIEND(P_1, O_1)` в $t{=}4$ усекает mark → окно $(O_1, X_2)$ немедленно 12 мес., распад $t{=}12$ — выжившая связь спасена; $(P_1, O_1)$ — свежий instance до $t{=}16$. Взаимный `FRIEND_REVOKE(O_1→P_1)` в $t{=}3$ добавил бы mark против $P_1$ на $[3, 12)$ — независимо от mark против $O_1$.

## 4. Базовые группы (L0)

<a id="l0-4"></a>

### 4.1 Принцип

<a id="l0-4.1"></a>

L0 — реальные малые группы. Membership — **непрерывный двусторонний предикат**: само-членство ∧ подтверждения группы ∧ link-опора. Ни ростер, ни запись не включают $P$ без подписи $P$; пребывание — при поддержке большинства. Вход двусторонен; revoke и выход — односторонни.

### 4.2 Объекты

<a id="l0-4.2"></a>

- <a id="l0-4.2.1"></a>**`MEMBER_OF(X,G)`** — «X member of G» (TTL, продлевается клиентом подписанта): подписант $P$: $P=X$ — само-членство; $P \ne X$ — подтверждение членства другого. Тип членства един для всех групп; различение сценариев — по типу ID группы: $ID_G$ — базовая группа L0, $ID_{GH}$ — сообщество иерархии, где живые `MEMBER_OF(P,GH)` образуют $R_{decl}(GH)$ и голосуют в C1-quorum ([HIER-5.2](#hier-5.2)).
- <a id="l0-4.2.3"></a>**`MEMBER_OF_REVOKE(X,G)`** с подписантом $X$ — выход: membership $X$ прекращается немедленно, односторонне.
- <a id="l0-4.2.4"></a>**`MEMBER_OF_REVOKE(X,G)`** с подписантом-подтверждающим — отзыв своего подтверждения; **quorum отзывов** роняет поддержку немедленно — это и есть исключение (события EXPEL не существует).

### 4.3 Roster computation (growth priority)

<a id="l0-4.3"></a>

Membership — это **выход детерминированного алгоритма** на $\tau$:

1. <a id="l0-4.3.1"></a>**Candidates:** все ключи $X$ с живым само-членством `MEMBER_OF(X,G)` (подписант = $X$).
2. <a id="l0-4.3.2"></a>**Cap-30 (до раундов):** если кандидатов $>30$, отбираются 30. Сначала учитывается число живых `MEMBER_OF(·,G)` от других кандидатов: подписант не должен совпадать с кандидатом, а счёт ведётся по уникальным подписантам (убыв.). При равенстве используется fresher $t_{sign}$ само-членства `MEMBER_OF`, а затем $pk$ (возр.). Непопавшие остаются кандидатами: записи не теряются, re-publish не нужен.
3. <a id="l0-4.3.3"></a>**Growth priority:** начальный roster состоит из **всех** отобранных кандидатов. Присоединение никогда не блокируется маргинальностью incumbents. Если укрупнённые пороги инвалидируют incumbents, они удаляются раундами (**squeeze-out** — принятая семантика, [LIM-10.16](#lim-10.16)).
4. <a id="l0-4.3.4"></a>**Synchronous rounds:** на каждом раунде **одновременно** удаляются все, нарушающие относительно текущего roster:
   <a id="l0-4.3.4-a"></a>(a) **кворум подтверждений:** живых `MEMBER_OF(·,G)` от текущих членов (подписант ≠ кандидат; само-членство в кворум не входит) ≥ $\lfloor |M|/2 \rfloor + 1$;
   <a id="l0-4.3.4-b"></a>(b) **cohesion:** активных связей с текущими членами ≥ $\lfloor |M|/2 \rfloor + 1$.
   Раунды повторяются до стабилизации. Результат **sound** (инварианты выполнены); **maximality не гарантируется** и не заявляется. Вычисление детерминировано.
5. <a id="l0-4.3.5"></a>**Freshness tie-break:** любые равные притязания в L0-вычислениях (cap, равные счёты) → fresher $t_{sign}$, затем $pk$.
6. <a id="l0-4.3.6"></a>**Quench:** $|M_{act}| < 4$ → roster пуст; edges от группы отваливаются мгновенным каскадом ([HIER-5.6](#hier-5.6)).

### 4.4 Динамика: две скорости

<a id="l0-4.4"></a>

- <a id="l0-4.4.1"></a>**Явные действия — мгновенны:** `MEMBER_OF_REVOKE` от себя (выход), quorum `MEMBER_OF_REVOKE` от подтверждающих (исключение), потеря cohesion (удаление раундом при следующем пересчёте).
- <a id="l0-4.4.2"></a>**Угасание — ≤ $T_{life}$:** expire без продления покрывает мёртвые узлы.
- <a id="l0-4.4.3"></a>**Вступление/возвращение:** материализация = живое само-членство `MEMBER_OF` + подтверждения других членов; после угасания поддержки — только заново набранный quorum. В норме продление тихое.
- <a id="l0-4.4.4"></a>Roster мгновенно входит в $R_{str}$ → пороги → edges ([HIER-5.6](#hier-5.6)).

### 4.5 Genesis

<a id="l0-4.5"></a>

`L0_GENESIS(initiator, descriptor, t_sign)` задаёт адрес $ID_G$ ([FMT-2.8](implementation.md#fmt-2.8)) — без привилегий. Группа жива, когда ≥ 4 участников удовлетворяют [L0-4.3](#l0-4.3) (их само-членства и взаимные подтверждения `MEMBER_OF` — обычные объекты). Церемоний нет: genesis — адрес, остальное — непрерывный предикат.

## 5. Эмерджентная иерархия

<a id="hier-5"></a>

### 5.1 Принцип

<a id="hier-5.1"></a>

Явные акты — связи и членство (`MEMBER_OF`) в группах L0 и сообществах. Edges, levels, валидность — выводимое состояние, перевычисляемое непрерывно.

### 5.2 Заявления о членстве (`MEMBER_OF`)

<a id="hier-5.2"></a>

1. <a id="hier-5.2.1"></a>**`MEMBER_OF(P, GH)`** — та же запись членства, что и в L0, для сообщества-вершины иерархии ($ID_{GH}$): подписанное $P$ утверждение «P member of GH» («я состою в $GH$»). Живые `MEMBER_OF(P, GH)` образуют $R_{decl}(GH)$; каждый — голос в C1-quorum **каждого** ребра $G \to GH$ с $P \in R_{str}(G)$. TTL $T_{life}$, тихо автопродлевается (rate-limit [ARCH-2.6.3](#arch-2.6.3)). Один `MEMBER_OF` голосует во всех соответствующих quorum — один человек, одно согласие; disjoint count по уникальным pk исключает двойной счёт.
2. <a id="hier-5.2.2"></a>**`MEMBER_OF_REVOKE(P, GH)`** — мгновенный односторонний отзыв (лёгкое возражение): живость `MEMBER_OF` обрезается в $t_{sign}$; quorum падает → edge отрывается мгновенно. Осцилляция REVOKE↔`MEMBER_OF` самонаказуема (отрыв мгновенный, возврат — через $T_{hold}$).
3. <a id="hier-5.2.3"></a>**Адрес группы** $ID_{GH}$ ([FMT-2.8](implementation.md#fmt-2.8)); имя — не identity ([LIM-10.1](#lim-10.1)); identity сообщества — структура. Различение сценариев членства — по типу ID группы: $ID_G$ — базовая группа L0 ([L0-4](#l0-4)), $ID_{GH}$ — сообщество иерархии.
4. <a id="hier-5.2.4"></a>**Isolate** — группа без живых детей: $R_{str} = \varnothing$, адрес не хранится сетью (владелец хранит), бутстрапится ([HIER-5.5](#hier-5.5)). `MEMBER_OF(P, GH)` от ключей $P$ вне живых $R_{str}$ к $GH$ не хранятся ([ARCH-2.6.1](#arch-2.6.1), [ARCH-2.4.9](#arch-2.4.9)).

### 5.3 Rosters

<a id="hier-5.3"></a>

1. <a id="hier-5.3.1"></a>$R_{decl}(GH)$ — участники с живыми `MEMBER_OF(P, GH)`: заявления, **не носители доверия, в порогах не участвуют**.
2. <a id="hier-5.3.2"></a>$R_{str}(GH) = \bigcup_{G \in \mathrm{children}(GH)} R_{str}(G)$ по уникальным pk; для L0 — активный roster [L0-4](#l0-4); isolate — $\varnothing$.
3. <a id="hier-5.3.3"></a>Участник «в иерархии» ⟺ состоит в валидной L0, транзитивно привязанной к доверенному компоненту.
4. <a id="hier-5.3.4"></a>Разделение ростеров исключает циркулярность.

### 5.4 Thresholds и disjoint count

<a id="hier-5.4"></a>

1. <a id="hier-5.4.1"></a>**Disjoint count.** Число участников с активной связью во внешнюю часть другого ростера определяется следующим образом:
$$U_{G_1 \Rightarrow G_2} = \big|\{\,X \in R_{str}(G_1):\ \exists\, O \in R_{str}(G_2) \setminus R_{str}(G_1),\ \text{связь } (X,O) \text{ активна}\,\}\big|$$
2. <a id="hier-5.4.2"></a>**Пороги** ($avg = (|G_1|+|G_2|)/2$, $\rho = |big|/|small|$, $f = f(avg)$, $\kappa = \kappa(avg)$). Сначала задаётся функция доли:
$$f(m) = \begin{cases} 0.5, & m < 30 \\ 0.05 + 0.45 \cdot 1.5^{-\log_{10}(m/30)}, & 30 \le m \le 10^4 \\ 0.05 + 0.1618 \cdot 4^{-\log_{10}(m/10^4)}, & m > 10^4 \end{cases}$$
$$\gamma(\rho) = \min(1,\ f + c(\rho-1)),\ c = 0.25;\qquad \kappa(m) = \min(\lfloor m/2.5 \rfloor,\ 4500)$$
$$t_{big} = \min\big(|big|,\ \max(\lfloor f \cdot |big| \rfloor,\ \kappa) + 1\big),\qquad t_{small} = \min\big(|small|,\ \max(\lfloor f \cdot |small| \rfloor,\ \lfloor \gamma \cdot |small| \rfloor,\ \kappa) + 1\big)$$
3. <a id="hier-5.4.3"></a>**Пара проходит** ⟺ $U_{G_1 \Rightarrow G_2} \ge t_{G_1}$ ∧ $U_{G_2 \Rightarrow G_1} \ge t_{G_2}$.
4. <a id="hier-5.4.4"></a>**Инварианты:** (i) при непустых внешних частях и полной взаимной внешней связности пара проходит (при большом пересечении ростеров внешние части малы — оговорка существенна); (ii) $t \le |side|$; (iii) равные пары: $t = \min(m, \max(\lfloor f\,m \rfloor, \kappa(m)) + 1)$; (iv) $\rho{=}1$, $m<30$: $t = \lfloor m/2 \rfloor + 1$; (v) асимметрия — цена до единогласия малой стороны.
5. <a id="hier-5.4.5"></a>**Лемма (инъекция одного ключа).** Угнанный аккаунт + 30 сибил-ключей: $U_{G_1 \Rightarrow G_2} = 30 \ge t_{G_1}$, но $U_{G_2 \Rightarrow G_1} = 1 < t_{G_2}$ — двусторонность отбивает инъекцию через один человеческий ключ.

### 5.5 Live edge: условия, активация, bootstrap, freeze

<a id="hier-5.5"></a>

<a id="hier-5.5.1"></a>

**Статусы групп:** *isolate* (0 живых детей, $R_{str} = \varnothing$, без уровня); *vertex* (2 живых ребёнка — предел бинарности, [HIER-5.5.15](#hier-5.5.15)); *free group* (1 живой ребёнок — возникает только понижением vertex; edge грандфатерится; приём одного ребёнка и привязка вверх — на общих основаниях).

<a id="hier-5.5.2"></a>

**Edge $G \to GH$ жив на $\tau$ ⟺ непрерывно:**

- <a id="hier-5.5.3"></a>**C1 (consent):** ≥ $\lfloor |G|/2 \rfloor + 1$ участников $R_{str}(G)$ имеют живые `MEMBER_OF(P, GH)`;
- <a id="hier-5.5.4"></a>**C2 (corroboration):** для **каждого** живого ребёнка $G_2 \in \mathrm{children}(GH) \setminus \{G\}$ — при бинарности он единственный ([HIER-5.5.15](#hier-5.5.15)) — пара $(G,G_2)$ проходит;
- <a id="hier-5.5.5"></a>**C3 (acyclicity):** не существует пути $GH \Rightarrow^* G$ по живым рёбрам.

**Активация.**

- <a id="hier-5.5.6"></a>**Attach к живой группе** (≥ 1 живого ребёнка у $GH$ и свободный детский слот — живых детей меньше двух, [HIER-5.5.15](#hier-5.5.15); $R_{str}(G) \ne \varnothing$ — иначе C1 невыполним): C1–C3 выполняются непрерывно $T_{hold}$ → активация. Проверка пар кандидата со всеми живыми детьми делает активацию безопасной для них.
- <a id="hier-5.5.7"></a>**Freeze ∥ hold window.** Freeze не приостанавливает накопление окна; активация в $\max(\text{конец freeze},\ \text{конец окна})$.
- <a id="hier-5.5.8"></a>**Freeze:** $T_f$ от `L0_GENESIS` и от bootstrap-активации вершины; блокирует только **новые** активации рёбер вверх; существующие рёбра и дети не затрагиваются.

**Bootstrap пустой группы $GH$:**

1. <a id="hier-5.5.9"></a>**Candidates** $K$: группы с живым C1-quorum к $GH$.
2. <a id="hier-5.5.10"></a>**S-set:** $S \subseteq K$, $|S| = 2$ — правило бинарности ([HIER-5.5.15](#hier-5.5.15)); все пары **внутри $S$** проходят. Существование одного $S$ достаточно — кандидаты вне $S$ ничего не блокируют (anti-DoS: сибил без внешних связей не входит ни в одно $S$).
3. <a id="hier-5.5.11"></a>**Окно:** для фиксированного $S$ — непрерывное выполнение условий всех его членов $\ge T_{hold}$; изменение состава $S$ (потеря члена, падение пары) перезапускает окно **этого** $S$; события кандидатов вне $S$ окно не перезапускает.
4. <a id="hier-5.5.12"></a>**Выбор при активации:** все $S$ имеют размер 2, поэтому среди $S$ с завершённым окном порядок определяется окном с более ранним стартом; при равенстве — лексикографически наименьший отсортированный список $ID$.
5. <a id="hier-5.5.13"></a>**Эффект:** $\mathrm{children}(GH) = S$; $R_{str}(GH) = \bigcup$; freeze $T_f$ для $GH$; прочие кандидаты присоединяются после по общим правилам attach.

<a id="hier-5.5.14"></a>

Одновременные активации оцениваются в детерминированном порядке — по $(t_{sign},\ H)$ объекта-условия; активированное ребро цикла создать не может (C3).

<a id="hier-5.5.15"></a>

**Бинарность объединений.** Сообщество объединяет не более двух групп: живых детей у $GH$ не больше двух. Attach возможен, только пока живых детей меньше двух; bootstrap активирует ровно двух кандидатов; дальнейший рост иерархии — бинарные объединения, то есть новая вершина создаётся над двумя сообществами. Структура, оказавшаяся более чем с двумя живыми детьми, пересчитывается на общих основаниях ([HIER-5.6.1](#hier-5.6.1), [HIER-5.6.2](#hier-5.6.2)).

### 5.6 Динамика: мгновенный пересчёт

<a id="hier-5.6"></a>

1. <a id="hier-5.6.1"></a>**Detach — мгновенный.** Провал C1 у edge **или** провал любой пары $(G_i, G_j)$ → **оба** edge пары отпадают немедленно; $GH$ пересчитывается немедленно.
2. <a id="hier-5.6.2"></a>**Понижение.** Живых детей $< 2$: при 1 — vertex → **free group** (edge грандфатерится, $L = 1 + L(\text{ребёнка})$); при 0 — **isolate**, восходящие edges отваливаются **тем же пересчётом** (C1 при пустом $R_{str}$ невыполним). Изолят привязывается **только bootstrap-ом**. Рёбра детей сохраняются; каскад — полный мгновенный пересчёт без искусственных задержек.
3. <a id="hier-5.6.3"></a>**Levels:** $L(GH) = 1 + \max_G L(G)$; isolate — без уровня; метаданные. При бинарности объединений ([HIER-5.5.15](#hier-5.5.15)) ширина вершины равна 2: $D \approx \log_2(N_{pop}/\overline{|L0|})$.
4. <a id="hier-5.6.4"></a>**Параллелизм:** multi-parenting — штатное состояние DAG; дети не блокируются ничем, кроме собственного freeze и свободного детского слота родителя (не более двух детей, [HIER-5.5.15](#hier-5.5.15)).
5. <a id="hier-5.6.5"></a>**Пересчёт:** непрерывный; пороги всегда по текущим структурным численностям (дрейф — [LIM-10.11](#lim-10.11)).

### 5.7 Возражения и выход

<a id="hier-5.7"></a>

1. <a id="hier-5.7.1"></a>**Лёгкое** — `MEMBER_OF_REVOKE`: quorum C1 падает, edge отрывается мгновенно.
2. <a id="hier-5.7.2"></a>**Тяжёлое** — `FRIEND_REVOKE` ([LINK-3.2](#link-3.2)).
3. <a id="hier-5.7.3"></a>**Выход группы из родителя** — массовый `MEMBER_OF_REVOKE` членов $G$; отдельного события нет.

### 5.8 Изоляция ботов

<a id="hier-5.8"></a>

`MEMBER_OF` permissionless, но: quorum L0 контролируются людьми; isolate имеет пустой $R_{str}$; disjoint count исключает co-membership; каждая пара на пути бот-поддерева в человеческую иерархию требует живых человеческих связей с TTL ≤ $T_{life}$. Одиночные edges (free groups) обхода не открывают: соединяющее ребро встречает сестёр (self-healing — оторванное от людей поддерево теряет корроборацию не позже $T_{life}$).

### 5.9 Мотивация связей

<a id="hier-5.9"></a>

Алгоритм не регламентирует, кого подтверждать; предполагается, что реальных связей достаточно для связывания графа.

## 6. Потребление доверия

<a id="trust-6"></a>

### 6.1 Proof membership

<a id="trust-6.1"></a>

Доказательство представляет собой **поддерево**, не путь: для каждого parent на пути предъявляются все живые дети, их перекрёстные связи (C2), численности $R_{str}$, живые `MEMBER_OF(P, GH)` (C1), а также собственная L0 заявителя (само-членства, подтверждения `MEMBER_OF` и связи). Это необходимо потому, что валидность одного edge — свойство всего множества детей.

Сильный режим — верификация по собственной replica (чистая функция состояния). Заявления о членстве в доверии не участвуют.

Commit-structures (Merkle-корни поддеревьев) для лёгких верификаторов относятся к планам развития ([ZKP-11](#zkp-11)).

### 6.2 Субъективная оценка

<a id="trust-6.2"></a>

Доверенное множество — транзитивное замыкание родителей L0 верификатора (+ его политика: размер, возраст, аномалии [DEF-7.4](#def-7.4)). Глобального флага «человек» нет. Практическая картина: люди — гигантский компонент; бот-кластеры — изолированные компоненты (структурно и транспортно).

### 6.3 Spot-check (SHOULD; расшифровка)

<a id="trust-6.3"></a>

<a id="trust-6.3-a"></a>

**Проблема.** Prover может утаить неблагоприятные записи (`MEMBER_OF_REVOKE`, `FRIEND_REVOKE`, распад связей). Верификатор без полной копии не видит неполноту предъявленного множества — это главный вектор обмана лёгкого верификатора.

<a id="trust-6.3-b"></a>

**Механизм.** Верификатор выбирает $k$ случайных участников из предъявленных rosters и запрашивает у них (транспорт — social graph верификатора / anti-entropy pull к собственной replica) записи, затрагивающие proof: живость `MEMBER_OF` и активность связей поддерева. Расхождение с предъявленным → reject.

<a id="trust-6.3-c"></a>

**Свойства.** Записи публичны в компоненте: утаивание prover'ом не мешает другим узлам ими владеть; обнаружение утаивания — с вероятностью $\approx 1-(1-p)^k$, где $p$ — доля опрошенных, владеющих противоречащей записью. Запросы liveness — вне гарантий.

<a id="trust-6.3-d"></a>

**Пределы.** Ограничения возникают при скоординированном сокрытии целым компонентом и при отсутствии у верификатора независимых путей к данным. Сильный режим (собственная replica) от этих пределов свободен.

<a id="trust-6.3-e"></a>

**Статус:** SHOULD — политика клиента; на консенсус не влияет.

## 7. Защитные механизмы

<a id="def-7"></a>

### 7.1 Гистерезис и freeze

<a id="def-7.1"></a>

$T_{hold}$ — окно непрерывного выполнения условий **перед активацией** (уведомления, возражения, дорост связей).

Отрыв мгновенный — асимметрия осознана: включение медленное, отторжение немедленное. Флаппинг подавляется ценой повторного включения. $T_f$ служит против накачки и ротации топологии; он параллелен hold window.

### 7.2 Decay и poison

<a id="def-7.2"></a>

Окна $T_{life}/(1+N)$, стекирование по разным парам, конечные метки, truce. Взаимные marks (≤2 на пару) — осознанная цена симметрии revoke: покинутый с обеих сторон получает двойное сжатие только от этой пары; каскад против одного ключа по-прежнему ограничен $\deg$.

### 7.3 Hijack, потеря ключа, боты

<a id="def-7.3"></a>

<a id="def-7.3.1"></a>

1. **Hijack.** Друзья публикуют `FRIEND_REVOKE` и `MEMBER_OF_REVOKE` (quorum). Окна сжимаются в $1+N$ ($T_{life}{=}12$ мес., $N{=}6$ — изоляция за ≈1.7 мес.); обновления требуют подписей друзей; их marks угонщик не аннулирует ([LINK-3.2.4](#link-3.2.4)). Угонщик может `MEMBER_OF_REVOKE` — рёбра отвалятся мгновенно; вред обратим. Бэйдейтинг `FRIEND_REVOKE` от имени жертвы точечными средствами не нейтрализуется: свежая подпись — правило разрешения конфликтов ([LINK-3.2.3](#link-3.2.3)), отметку подделки она не стирает. Средство против подделки задним числом — `KEY_LOSS` ([ARCH-2.3.2](#arch-2.3.2)): полный отзыв ключа гасит все его записи, включая поддельные; `KEY_LOSS` рекомендуется при любом подозрении на компрометацию, даже разовой.

<a id="def-7.3.2"></a>

2. **Честное восстановление.** Переверберация лично → друзья подписывают `FRIEND` (marks обоих направлений аннулируются, instances чисты) → заявления `MEMBER_OF` возобновляются. Без «штрафа переживания».

<a id="def-7.3.3"></a>

3. **Потеря ключа (ротация) — рецепт:** при сохранении контроля над секретом (потеря/компрометация) первая ссылка — `KEY_LOSS` ([ARCH-2.3.2](#arch-2.3.2)): все записи ключа мгновенно невалидны, без poison marks и штрафов → новый ключ вступает в L0 (само-членство `MEMBER_OF` + кворум подтверждений) → связи переподписываются контрагентами (`FRIEND` — truce чистит метки пар). Без контроля секрета (угон) — как раньше: старый выводится друзьями, quorum `MEMBER_OF_REVOKE` (само-выход недоступен — ключ у вора; hijack-механика — [DEF-7.3.1](#def-7.3.1)). Marks не переносятся (привязаны к ключу); вору quorum не собрать; ботам ротация бесполезна. Непрерывность «тот же человек» — негарантия ([LIM-10.2](#lim-10.2)).

<a id="def-7.3.4"></a>

4. **Боты.** Не проходят порогов без человеческих связей ([HIER-5.8](#hier-5.8)).

### 7.4 Обнаружение аномалий (advisory)

<a id="def-7.4"></a>

Churn (`FRIEND`/`FRIEND_REVOKE` циклы, осцилляции); каскадные revoke против одного pk; массовые `FRIEND` после каскада («прощение-фишинг»); синхронные `MEMBER_OF`/`MEMBER_OF_REVOKE`, спам адресов, набеги, namespace-спуфинг; звёздные топологии; распределения степеней/плотности; синхронность операций; динамика L0 (синхронные вступления/отзывы, squeeze-out паттерны, growth-атаки); накачка уровней, цепочки одиночных детей; DAG-специфика (штормы привязок, близнецы-родители); паттерны memo.

## 10. Ограничения и открытые вопросы

<a id="lim-10"></a>

<a id="lim-10.1"></a>

1. **Namespace:** проблема имперсонации имён нерешаема; identity определяется структурой.

<a id="lim-10.2"></a>

2. **Многоличность:** принципиально не обнаруживается. Стоимость связей и эвристики смягчают эту проблему.

<a id="lim-10.3"></a>

3. **Публичность согласия:** видны составы и MEMBER_OF-заявления; приватизация — [ZKP-11](#zkp-11).

<a id="lim-10.4"></a>

4. **Мажоритарная жёсткость:** индивидуум не привяжется без большинства своей L0.

<a id="lim-10.5"></a>

5. **Сговор выше порогов:** выше $\kappa$ — вне гарантий.

<a id="lim-10.6"></a>

6. **Спам:** структурно ограничен; остаточное — объёмы буферов.

<a id="lim-10.7"></a>

7. **Грифинг ядом:** каскады сжимают окна; взаимные marks (≤2 на пару) усиливают взаимный грифинг пары; ограничители — конечность, truce; остаточный риск признан.

<a id="lim-10.8"></a>

8. **Hijack и клиентские политики:** явные подтверждения операций; предупреждения о контрагентах с историей revoke.

<a id="lim-10.9"></a>

9. **Цензура соседа:** сосед может утаивать записи. Anti-entropy и multi-parenting смягчают эту проблему; единственный мост остаётся риском.

<a id="lim-10.10"></a>

10. **Доступность данных:** prover может скрывать записи; spot-check ([TRUST-6.3](#trust-6.3)) смягчает; скоординированное сокрытие — остаточный риск.

<a id="lim-10.11"></a>

11. **Дрейф порогов при росте:** рост брата повышает парный порог при статичных связях — мгновенный detach и дорогой возврат ($T_{hold}$); живучесть — multi-parenting.

<a id="lim-10.12"></a>

12. **Сложность вывода:** бинарность объединений ([HIER-5.5.15](#hier-5.5.15)) делает парные проверки линейными по числу рёбер ($k \le 2$); обязательны индексы и инкрементальность.

<a id="lim-10.13"></a>

13. **Консервативность rounds:** синхронное удаление — не максимальный roster; осознанно (soundness важнее полноты).

<a id="lim-10.14"></a>

14. **Расхождения часов:** влияют на мгновенные виды, но не на сходимость; $\Delta$ покрывает скью.

<a id="lim-10.15"></a>

15. **Управление параметрами:** изменение означает форк; governance не специфицирован.

<a id="lim-10.16"></a>

16. **Squeeze-out (growth priority):** присоединение может вытеснить incumbents на пороге вплоть до quench; враждебный join стоит кворума подтверждений и разрушает также членство атакующего; осознанная цена детерминизма и отсутствия задержек.

<a id="lim-10.17"></a>

17. **Транспортная инженерия:** relay-политика, пропускная способность, объёмы хранилищ — вне спецификации.

## 11. Приватность через ZKP (roadmap, вне базовой версии)

<a id="zkp-11"></a>

<a id="zkp-11.1"></a>

Эскиз решения включает обязательства Педерсена, деревья Меркла ростеров, публичные корни, уровни и численности, нуллификаторы и рекурсивную агрегацию.

**Открытые блокеры:** доказуемое воспроизведение LWW по $t_{sign}$ и reconstruction (кламп, mutual marks) в схемах; TTL-объекты и обновления обязательств; commit-structures для лёгких верификаторов ([TRUST-6.1](#trust-6.1)); поиск кандидатов без публичного графа; масштаб; постквантовость.
