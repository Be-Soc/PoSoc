# Contributing to PoSoc

Спасибо за интерес к проекту PoSoc (Proof of Social) — спецификации децентрализованной сети доверия.

## Структура репозитория

- `specs/` — спецификация протокола: `specs/concept.md` — базовые принципы, алгоритмы, математика и гарантии; `specs/implementation.md` — детали реализации (форматы записей, канонизация, криптография, транспорт); `specs/glossary.md` — глоссарий. Оглавление — `specs/index.md`.
- `LICENSE` — условия использования.

## Как вносить изменения

### 1. Изменения спецификации

Спецификация нормативна: любое изменение семантики протокола (записи, revoke-семантика, пороги, параметры, гарантии/негарантии) вносится **только** в `specs/concept.md` или `specs/implementation.md` (см. `specs/index.md`). Изменения принципов/алгоритмов/математики — в `concept.md`; изменения форматов записей, канонизации, криптографии и транспорта — в `implementation.md`.

**Все файлы спецификации должны всегда поддерживаться в актуальном состоянии.** Изменение, затрагивающее несколько разделов или оба каталога, обязано обновлять все затронутые файлы в одном PR — рассинхронизация недопустима.

- Перед изменением откройте issue с описанием проблемы, которую решает правка.
- Изменения семантики (§2–§7) и параметров (§9) требуют обоснования: модель угроз (§1.3), стоимость атаки, совместимость с инвариантами.
- При изменении терминов обновляйте GLOSSARY (`specs/glossary.md`) — определения должны оставаться согласованными с текстом.
- При изменении параметров (§9) проверьте согласованность примеров и справочных таблиц порогов в том же разделе.
- При изменении списка разделов (новый/переименованный файл) обновляйте `specs/index.md` в том же изменении.
- Версию спецификации в `specs/concept.md` и `specs/index.md` повышайте при смысловых изменениях; опишите изменение в начале commit message.

### 2. Стиль

- Каждому утверждению спецификации присвоен стабильный ID `PREFIX-§.N` (доменный префикс + §-адрес; вложенные подпункты — суффиксы `-a`, `-b`, …), проставленный явным якорем `<a id="…"></a>`. Карта префиксов: `PRIN-` (принципы), `ARCH-` (архитектура), `FMT-` (форматы записей), `LINK-` (связи), `L0-` (базовые группы), `HIER-` (иерархия), `TRUST-` (потребление доверия), `DEF-` (защита), `CRYPTO-` (криптография), `PARAM-` (параметры), `LIM-` (ограничения), `ZKP-` (приватность), `REF-` (эталонные реализации), `GLOS-<термин>` (глоссарий). Префикс принадлежит строго своему файлу. Префиксы `PRIN/ARCH/LINK/L0/HIER/TRUST/DEF/PARAM/LIM/ZKP` находятся в `specs/concept.md`; `FMT/CRYPTO/REF` — в `specs/implementation.md`; `GLOS` — в `specs/glossary.md`. По решению владельца `ARCH-2.2.4`, `ARCH-2.2.5`, `ARCH-2.2.x-impl` и `ARCH-2.5` находятся в `specs/implementation.md`, а остальные `ARCH` — в `specs/concept.md`.
- Перекрёстные ссылки на утверждения — markdown-ссылки по ID с якорями: `[LINK-3.2.4](specs/concept.md#link-3.2.4)` (внутри файла — `#id`). Ссылки вида «§N.N» используются в тексте как обозначения разделов и не заменяют ссылки на утверждения.
- **ID не перенумеровываются и не переиспользуются.** Новый пункт получает следующий свободный §-адрес (в конец списка); при удалении/перемещении утверждения его ID сохраняется (текст может переехать, якорь — нет). Удалённый ID не присваивается заново.

- Язык спецификации — русский; термины, имена записей (`FRIEND`, `MEMBER_OF`, `KEY_LOSS` и т.п.) — на английском.
- Математические формулы — LaTeX-нотация (`$...$`, `$$...$$`).
- Нумерация разделов стабильна: ссылки вида `§3.2.4` используются по всему тексту. Правила сохранения ID и добавления новых пунктов приведены выше.
- Каждое изменение согласуйте с принципами §1.2 и моделью угроз §1.3: если правка расширяет или сужает гарантии — явно отразите это в §1.3.

### 3. Документация

Каталог `docs/` — человекочитаемые объяснения протокола. Документация не дублирует спецификацию и не является нормативной: она объясняет и ссылается, спецификация — источник истины. При конфликте документации со спецификацией чинится документация, а не спека.

Действующие документы:

- `docs/posoc-concept.md` — технический обзор концепции протокола: принципы, алгоритмы, математика, гарантии (для инженеров, оценивающих интеграцию). Не ссылается на implementation-материалы.
- `docs/posoc-implementation.md` — детали реализации: криптография, форматы записей, транспорт и узловая механика. Может ссылаться на concept, но не наоборот.
- `docs/posoc-plain.md` — изложение основных механик простым языком без специальной терминологии (для читателей вне ИТ).

Правила:

- **Актуальность.** Любое изменение спецификации, затрагивающее описанное в документации поведение, обновляет затронутые документы и `docs/index.md` в том же PR — рассинхронизация недопустима, устаревшие утверждения переписываются или удаляются (не «оставляются для истории»).
- **Обязательные элементы** каждого документа: аннотация в самом верху (что покрывает и для кого написан) и секция «References» (ссылки на спецификацию и смежные документы с пояснением, что каждый даёт).
- **Аудитория.** Один документ — одна аудитория. Технические документы могут использовать термины спецификации; документ для нетехнических читателей (`posoc-plain.md`) не использует специальный термин без немедленного объяснения бытовыми словами.
- **Тон `posoc-plain.md` — эталонный** (закреплён владельцем): спокойный, точный, взрослый — стиль хорошей деловой журналистики. Аналогии — из деловой/правовой/социальной жизни взрослого человека (нотариально заверенное заявление, рекомендательное письмо с ограниченным сроком, членство в объединении) и дозированно. Запрещены: «детские» метафоры (тетрадь, пятна, кружки, острова, тропинки), уменьшительные формы, снисходительный тон, риторические восторги; ИТ-лексика (hash, сервер, алгоритм) — по возможности избегать. Новые/обновляемые не-технические документы выдерживаются в этом же стиле.
- **Ссылки, не пересказ.** Документ ссылается на разделы `specs/` вместо копирования формулировок, форматов и таблиц параметров. Числа допустимы только как иллюстрация с ссылкой на нормативный источник. Разделение каталогов specs распространяется на docs: concept-документация не ссылается на implementation-материалы (в том числе на `docs/posoc-implementation.md`); implementation-документация может ссылаться на concept.
- **Мотивация.** Нетривиальные решения объясняются вместе с «почему»: какое ограничение заставило, какая альтернатива отвергнута.
- **Новый документ** добавляется строкой в `docs/index.md` в том же изменении; удалённый — убирается из индекса. Язык документации — русский.

### 4. Процесс

1. Fork / ветка от `main`.
2. Внесите изменения в соответствующие файлы `specs/` (все затронутые разделы — в одном PR).
3. Проверьте внутреннюю согласованность: перекрёстные ссылки `§x.y`, GLOSSARY (`specs/glossary.md`), таблицу параметров (`specs/concept.md`), примеры, актуальность `specs/index.md`.
4. Откройте Pull Request с описанием: мотивация, затронутые разделы, влияние на гарантии.

### 5. Что не принимается

- Реализации, клиентский код, транспортная инженерия — вне скоупа репозитория (§2.2.4, §8.6, §12): спецификация нормативна, реализации — отдельный артефакт.
- Изменения, смягчающие гарантии без явного анализа стоимости атаки.
